## 1. BaseModel 基础模型
除 AuthUser 外，所有数据模型均继承自 BaseModel。BaseModel 统一定义公共字段，避免重复。

**BaseModel 字段定义**：

|字段名     |	类型	|必填	|说明|
| :--- | :--- | :--- | :--- |
|recordcode	|Char(64)	|是	系统全局唯一编码，由后端在创建时自动生成，不可修改|
|created_at	|DateTime	|是	创建时间（自动）|
|updated_at	|DateTime	|是	更新时间（自动）|
|is_active	|Boolean	|是	是否激活（软删除兼容标记），默认为 True|
|is_deleted	|Boolean	|是	软删除标记，默认为 False|
**recordcode自动生成规则：**

```text
{prefix}-{YYYYMMDD}-{8位大写UUID}

示例：ASSET-20260708-A3F9B2E1
```
- `prefix`：每个模型自定义的前缀（见各模型定义）
- `YYYYMMDD`：当前日期（timezone.now()）
- `8位大写UUID`：uuid.uuid4().hex[:8].upper()

**BaseModel 继承说明**：

- 子类通过`RECORDCODE_PREFIX` 类属性定义自己的前缀
- `recordcode` 在 `save()` 方法中自动生成（若为空）
- `is_deleted` 配合 `SoftDeleteManager` 实现软删除查询
- `AuthUser` 因继承 Django 的 `AbstractBaseUser`，不继承 BaseModel，单独定义字段

**业务编码唯一性通用规则**：

所有模型中的 {model}_code 类字段（如 asset_code、contract_code、department_code、employee_jobcode 等）均遵循以下规则：

> **唯一性约束仅对未删除记录生效**（`is_deleted=False`） 。软删除（`is_deleted=True`）的记录不参与唯一性校验，允许存在多条 is_deleted=True 且业务编码相同的记录，也允许在已存在软删除记录的情况下，重新创建相同业务编码的新记录。

实现方式（Django）：

```python
class Meta:
    constraints = [
        models.UniqueConstraint(
            fields=["asset_code"],
            condition=models.Q(is_deleted=False),
            name="unique_asset_code_not_deleted",
        ),
    ]
```

|type_name	    |Char(100)	|是	| 类型名称，业务唯一（仅未删除记录）|
|parent	        |FK(self)	|否	| 上级类型 FK（指向 recordcode），null 表示根类型|

- 创建/移动时自动维护 `path` 物化路径。

**索引**：

- `type_code`（条件唯一，仅 `is_deleted=False`）
- `type_name`（条件唯一，仅 `is_deleted=False`）
- `parent`（FK 索引）
- `path`（普通索引，加速子孙查询）
- `level`（普通索引）

继承自 BaseModel 的字段：recordcode、created_at、updated_at、is_active、is_deleted

asset_code 自动生成规则：

asset_code 由后端在创建资产时根据关联的资产类型层级自动生成，格式如下：

```text
{一级类型编码}-{二级类型编码}-{三级类型编码}-{8位大写UUID}
具体规则：

从 asset_type_recordcode 关联的 AssetType 记录出发
沿 parent_code 链向上追溯到根类型（level=0）
按层级从根到叶子顺序拼接所有 type_code
最后追加 -{uuid.uuid4().hex[:8].upper()}
```
**性能优化说明**：
层级追溯查询可通过以下方式优化：
1. AssetType表已建立parent_code索引，支持快速向上追溯
2. 建议在Service层缓存类型层级路径（如Redis），减少重复查询
3. 层级最多6层（level 0~5），查询深度可控

示例：

假设资产类型层级为：

根类型：type_code="IT"（level=0）

二级类型：type_code="COMPUTER"（level=1，parent=根）

三级类型：type_code="NOTEBOOK"（level=2，parent=二级）

则新建该类型资产时，asset_code 自动生成为：

```text
IT-COMPUTER-NOTEBOOK-A3F9B2E1
```
特殊情况处理：
若资产类型仅有1级（根类型）：{type_code}-{8位大写UUID}
若资产类型有2级：{一级type_code}-{二级type_code}-{8位大写UUID}
若资产类型有3级及以上：依次拼接所有层级 type_code，中间用 - 连接，最后追加 -{8位大写UUID}

**业务规则**：

asset_code 在 is_deleted=False 的记录中必须唯一；软删除后不占用唯一性，允许重新创建相同 asset_code 的新资产。

asset_code 一旦创建不可修改。

usage_type 在入库时自动为new，出库时自动锁死为used，后续不再变动。

physical_grade 在回收或维修完成后更新。

索引：

asset_code（条件唯一，仅 is_deleted=False）

qr_code（条件唯一，仅 is_deleted=False）

asset_current_status（普通索引）

asset_type_recordcode（外键索引）

asset_storage_recordcode（外键索引）

asset_manager_recordcode（外键索引）

is_deleted（普通索引）

created_at（普通索引）

不继承 BaseModel（因继承 Django AbstractBaseUser + PermissionsMixin）

字段名	类型	必填	说明

recordcode	Char(32)	是	系统全局唯一编码

**软删除策略说明**：
AuthUser使用Django原生的`auth_is_active`字段作为软删除标记，而非BaseModel的`is_deleted`。原因：
1. Django AbstractBaseUser内置`is_active`字段，与认证系统深度耦合
2. 将`auth_is_active=False`等效于"软删除"，禁用用户登录权限
3. 唯一性约束条件为`auth_is_active=True`，与BaseModel模型的`is_deleted=False`逻辑等价
4. 实际删除用户时，将`auth_is_active`设为False即可，无需物理删除

业务规则：

auth_is_active=False 的用户无法登录。

auth_username、email、auth_phone 在 auth_is_active=True 的记录中必须唯一（软删除兼容策略，使用 Django 原生 auth_is_active 作为有效状态标记，而非 is_deleted）。

索引：

auth_username（条件唯一，仅 auth_is_active=True）

email（条件唯一，仅 auth_is_active=True）

auth_phone（条件唯一，仅 auth_is_active=True）
