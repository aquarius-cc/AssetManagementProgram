## 3. Docker 编排

### 3.1 docker-compose.yml（M-41 对齐实际编排）

> 唯一事实源 = 仓库内 `asset_management_backend/docker-compose.yml` / `docker-compose.prod.yml` / `docker-compose.monitoring.yml`。本节为服务清单概览，**不复述完整 YAML**（历史版本此处内嵌的 compose 示例与实际文件漂移严重，已删除——以仓库文件为准）。

| 服务 | 镜像/构建 | 职责 |
|:---|:---|:---|
| `web` | 构建（后端 Dockerfile） | Django + gunicorn 业务服务 |
| `postgres` | postgres:16 | 主库 |
| `redis` | redis:7-alpine | 缓存/队列 |
| `nginx` | 构建（`docker/nginx/Dockerfile` 双阶段，见 §3.3） | 前端静态 + 反代 + TLS 三态渲染 |
| `certbot` | 构建（certbot sidecar） | 首签/续期（§5） |
| `backup` | 构建（`docker/backup/Dockerfile`） | 定时备份（§6） |

共享卷：`letsencrypt-certs`（nginx `:ro` + certbot 写）、`certbot-webroot`（HTTP-01 验证）、备份卷（`BACKUP_DIR` / `BACKUP_DIR_REDIS` / `BACKUP_DIR_MEDIA` 三目录）。网络：`asset-network`。

### 3.2 后端 Dockerfile

```dockerfile
FROM python:3.12-slim

WORKDIR /app

RUN apt-get update && apt-get install -y --no-install-recommends \
    libpq-dev gcc && \
    rm -rf /var/lib/apt/lists/*

COPY requirements/ /app/requirements/
RUN pip install --no-cache-dir -r requirements/prod.txt

COPY . /app/

EXPOSE 8000

CMD ["gunicorn", "config.wsgi:application", \
     "--bind", "0.0.0.0:8000", \
     "--workers", "4", \
     "--timeout", "120"]
```

### 3.3 前端与 nginx 编排（M-41 对齐实际双阶段构建）

实际文件 = `docker/nginx/Dockerfile`（**以仓库文件为准，下方为结构摘要**）。不存在独立的「前端 Dockerfile + COPY nginx.conf」形态，也**无需 `mkdir dist` 前置步骤**：

```dockerfile
# Stage 1：前端构建（node:20-alpine AS frontend-build）
COPY vue-assetmanagement/package*.json ./   # 先拷依赖清单，npm ci 层缓存
COPY vue-assetmanagement/ ./
RUN npm ci && npm run build                  # 产物在 /app/dist

# Stage 2：nginx:1.27-alpine
COPY docker/nginx/nginx.conf /etc/nginx/nginx.conf
COPY docker/nginx/conf.d/   /etc/nginx/conf.d/        # *.tpl 三态模板（§5）
COPY docker/nginx/entrypoint.sh /docker-entrypoint-custom.sh
COPY --from=frontend-build /app/dist /app/dist        # 仅 dist 进终镜像
```

要点：构建上下文为**仓库根**（`compose build nginx` 或 `docker build -f asset_management_backend/docker/nginx/Dockerfile .`），前端产物经 `COPY --from=frontend-build` 只带 `dist`；entrypoint 按证书存在性渲染三态模板（§5.1）。

### 4.2 升级部署（M-41 对齐 docker compose 栈）

> 实际部署形态为 docker compose（§3），无 systemd 单机服务；原「systemctl restart」步骤系单机裸跑旧方案残留，已删除。

```bash
# 1. 拉取最新代码（含子模块指针）
git pull origin main
git submodule update --init --recursive

# 2. 重建镜像（代码变更的服务的依赖镜像）
docker compose build web nginx

# 3. 执行迁移（web 容器内，无数据丢失）
docker compose run --rm web python manage.py migrate

# 4. 滚动重启变更服务
docker compose up -d web nginx

# 5. 健康检查
docker compose ps
curl -fsS http://localhost/api/v1/health/   # 以实际 health 端点为准
```

## 5. HTTPS 证书：首次签发 / 自动续期 / 故障排查与验证清单（M-37 / M-41 联动章节）

> 本章为批次 2 M-37 落地的新增章节；文档其余章节的整体重写仍属批次 6 的 M-41，不在本批范围。

### 5.1 机制概览（三态状态机）

| 态 | 触发条件 | 行为 |
|:---|:---|:---|
| 态1 引导态 | `${CERT_PATH}/fullchain.pem` 不存在（全新首装 / 证书卷丢失） | nginx 渲染 `default-http.conf.tpl`：80 端口承载全部业务路由（API/health/ws/静态/SPA），无 TLS 块、无 HSTS 头；certbot sidecar 可经 webroot 完成 HTTP-01 验证 |
| 态2 首现切换 | 证书从无到有 | `cert-watch.sh` 重渲染完整 TLS 模板（`default.conf.tpl`）+ `nginx -t` + reload——仅 reload 不换已渲染的 HTTP-only 配置，重渲染是必经步骤 |
| 态3 轮换续期 | 证书指纹变化（certbot 续期写入新文件） | `cert-watch.sh` `nginx -t` + reload。nginx 将证书缓存于内存，不 reload 会持续提供旧证书 |

关键组件：

- `docker/nginx/entrypoint.sh`：按证书存在性选模板渲染 + `nginx -t` + 后台启动 cert-watch + `exec nginx`。
- `docker/nginx/scripts/cert-watch.sh`：30s 固定轮询，busybox `sha256sum` 指纹比对（fullchain+privkey 拼接哈希）；`nginx -t` 失败不 reload，等下轮。
- `docker/nginx/scripts/renew.sh`（certbot sidecar）：12h 一轮；有证书走 `certbot renew --webroot`，无证书走 `certbot certonly --webroot` 首签；首签失败 1h→2h→4h…24h 封顶翻倍退避（防 Let's Encrypt 429 速率限制）。`EMAIL` 环境变量可选注入（不注入则无邮箱注册，仅收不到 LE 到期提醒）。
- 证书路径对齐：nginx 读 `${CERT_PATH}/fullchain.pem`，compose 注入 `CERT_PATH=/etc/nginx/letsencrypt/live/${DOMAIN}`，与 certbot 产出点一致（`letsencrypt-certs` 共享卷，nginx 侧 `:ro`）。

### 5.2 首次部署操作步骤（全新服务器）

```bash
# 0. 前置：域名 A 记录已指向服务器，80/443 安全组放行
# 1. 配置域名与（可选）签发联系邮箱
export DOMAIN=example.com
export EMAIL=admin@example.com        # 可选；不设置则 --register-unsafely-without-email

# 2. 启动（证书为空，nginx 自动进入态1 引导态，80 端口业务可用）
docker compose up -d

# 3. 首签（自动）：certbot sidecar 下一轮（≤12h）自动 certonly；
#    急用可手动触发同款命令（原 setup-https.sh 已下线——其占位证书写入
#    非挂载路径必然丢失，属假象链路，勿再使用）：
docker compose exec certbot certbot certonly --webroot \
    --webroot-path=/var/www/certbot --non-interactive --agree-tos \
    ${EMAIL:+--email=$EMAIL} -d "$DOMAIN"

# 4. 验证切换（≤30s 内 cert-watch 完成态2）：
curl -I https://$DOMAIN/health/    # 期望 200
```

### 5.3 验证清单（每次变更 / 灰度验收逐项执行）

1. `curl -I http://$DOMAIN/health/` → 200（态1 时唯一可达入口）。
2. `curl -I https://$DOMAIN/health/` → 200（态2/态3）。
3. **reload 生效证明**：`openssl s_client -connect $DOMAIN:443 -servername $DOMAIN </dev/null 2>/dev/null | openssl x509 -fingerprint -sha256` 与宿主机 `docker compose exec nginx sha256sum $CERT_PATH/fullchain.pem` 对应证书指纹一致。
4. 容器健康：`docker compose ps` nginx 为 healthy（HEALTHCHECK 探 `/health/`，两个模板下均真实代理到后端，无假绿）。
5. OCSP 告警说明：`ssl_stapling on` 在 Let's Encrypt **staging** 证书下会告警（stapling 失败仅 warning，不阻断启动），属预期现象，勿误判为故障。

### 5.4 staging 验证口径（本地 / 无公网域名环境）

真实 Let's Encrypt 签发有速率限制且需公网可达域名，本地验证用 staging：

```bash
docker compose exec certbot certbot certonly --webroot \
    --webroot-path=/var/www/certbot --non-interactive --agree-tos \
    --staging -d "$DOMAIN"
```

[M-41] 两条硬验收（部署完成必做）：

1. **空证书目录首次启动**：清空 `${CERT_PATH}` 对应卷后 `docker compose up -d`——态1 引导态下业务在 80 端口可用（API/静态/SPA 全路由），`cert-watch.sh` 30s 轮询内在证书出现后切态2。
2. **深链刷新**：`curl -I https://$DOMAIN/main/assetdetails` 期望 **200**（nginx `try_files ... /index.html` 承接 SPA 路由；两份 tpl 均已具备，复核项）。

staging 证书链不受浏览器信任（curl 需 `-k`），但**三态状态机切换、reload、指纹一致性验证全部真实**；生产首签留到灰度环境做一次。

### 5.5 故障排查

| 现象 | 排查 |
|:---|:---|
| nginx 起不来，报 `ssl_certificate` 文件不存在 | 旧镜像/旧渲染产物残留：确认 `CERT_PATH` 为 `.../live/${DOMAIN}` 且模板为三态版本；`docker compose logs nginx` 看 `tpl=` 与 `state=` 输出 |
| 443 可达但证书是旧的（续期后） | cert-watch 是否在跑：`docker compose exec nginx ps | grep cert-watch`；查 `[cert-watch]` 日志；确认没有按 renew.sh 旧注释删掉 watcher |
| 首签反复失败 | `docker compose logs certbot`；确认 80 端口公网可达、DNS 已生效（`dig $DOMAIN`）；退避上限 24h 内不会重试过早； staging 先验证链路再切生产 |
| 态1 期间 https:// 不可达 | 预期行为（引导态无 TLS），首签完成 + 态2 reload 后自动恢复 |

## 6. 备份与恢复演练（M-41 新增，对齐实际脚本与 compose backup 服务）

> 唯一事实源 = `asset_management_backend/scripts/`（backup.sh / redis_backup.sh / media_backup.sh / backup_verify.sh / backup_status.sh / restore_test.sh）与 compose `backup` 服务（构建自 `docker/backup/Dockerfile`，注入 `BACKUP_DIR=/data/backups/postgres`、`BACKUP_DIR_REDIS`、`BACKUP_DIR_MEDIA`）。prod 变体见 `docker-compose.prod.yml` 的 `backup` 服务；备份状态指标经 `backup_status_data` 共享卷对接监控（N-2）。

### 6.1 备份产物

| 对象 | 脚本 | 产物路径 | 格式 |
|:---|:---|:---|:---|
| PostgreSQL 全量 | backup.sh | `${BACKUP_DIR}/full_*.dump` | pg_dump `--format=custom`（pg_restore 可恢复） |
| Redis | redis_backup.sh | `${BACKUP_DIR_REDIS}/` | RDB/AOF 快照 |
| 媒体文件 | media_backup.sh | `${BACKUP_DIR_MEDIA}/` | 文件打包 |

### 6.2 校验与状态

```bash
# 产物完整性校验（backup_verify.sh：pg_restore --list 抽检 dump 可读性）
docker compose exec backup bash /app/scripts/backup_verify.sh

# 备份新鲜度/状态（backup_status.sh：最新产物时间与大小，供 N-2 textfile 指标）
docker compose exec backup bash /app/scripts/backup_status.sh
```

### 6.3 恢复演练步骤（季度演练，记录入下表）

```bash
# 1. 取最新全量 dump
LATEST=$(ls -t ${BACKUP_DIR}/full_*.dump | head -1)

# 2. restore_test.sh：在临时库恢复并做行数抽检（不触碰生产库）
docker compose exec backup bash /app/scripts/restore_test.sh "$LATEST"

# 3. 人工核对关键表行数与最近业务时间戳
```

### 6.4 RPO / RTO 口径

- **RPO**：以 backup.sh 调度周期为准（compose 定时触发），全量备份间隔内的增量丢失为可接受上限；关键表以恢复后最新 `updated_at` 实测。
- **RTO**：恢复演练实测（临时库 restore + 抽检）耗时 + 应用重连时间；目标以运维侧 SLA 为准，演练记录须含实测值。
