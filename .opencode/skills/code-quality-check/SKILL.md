# 项目级代码质量审查 (Code Quality Check)

> 从 `docs/Review/Review.md` 提炼的方法论 skill，保留完整审查框架，项目特定内容动态加载。

## §0 角色设定

你是一位资深全栈架构师和代码审查专家，精通本项目的技术栈（参见 README.md）。你已阅读并承诺遵守根级 `AGENTS.md` 及其引用的全部规范。

## §1 强制前置（每次触发必须执行）

执行任何审查前，**必须**按顺序读取以下文件并确认理解：

1. `README.md` — 项目全貌
2. `AGENTS.md` — 根级宪法（CT/DR/SC/OC/AR/Style/Fact 全部规则）
3. `asset_management_backend/AGENTS.md` — 后端子引擎
4. `vue-assetmanagement/AGENTS.md` — 前端子引擎
5. `Rules_Fiels/backend-business-rules.md` — 后端业务规则
6. `Rules_Fiels/backend-testing-rules.md` — 后端测试规则
7. `Rules_Fiels/frontend-business-rules.md` — 前端业务规则
8. `Rules_Fiels/frontend-testing-rules.md` — 前端测试规则
9. `Rules_Fiels/Duplicate_Codes/complete-patterns.md` — 重复代码活账本

若发现违反上述任意规则，必须在审查结果中标注，并说明是否触发 `[HALT]`。

## §2 审查范围（动态确定）

默认审查 `git diff` 中的未暂存/已暂存改动。用户可指定文件或目录。

**后端目录**：`asset_management_backend/apps/`、`core/`、`utils/`、`config/`
**前端目录**：`vue-assetmanagement/src/`（components、composables、views、stores、router、utils、types）
**忽略**：`node_modules`、`dist`、`__pycache__`、`.git`、`venv`、自动生成的 `migrations/`

## §4 审查方法（11 步）

1. 输出审查计划、模块清单、所需文件清单，等用户确认后再进入代码审查。
2. 建立"需求功能清单" → "后端接口清单" → "前端调用清单" → "数据模型/状态机清单"。
3. 对每个核心流程追踪全链路：前端页面 → Pinia store → API → DRF URL → View 权限 → Serializer → Service → Selector → Model/DB → 响应 → 前端渲染。
4. 对每个 API 检查：路径、方法、参数、响应结构、错误码、分页、过滤、排序、幂等性。
5. 对每个前端页面检查：路由、权限、状态管理、API 调用、错误处理、加载态、空态。
6. 对每个状态转换检查：触发动作、权限、前置条件、后置状态、副作用、审计、通知、测试。
7. 对关键操作检查：`@transaction.atomic`、并发、重复提交、回滚。
8. 对权限检查：RBAC 角色、行级隔离、后端校验、前端路由/按钮控制。
9. 对可观测性检查：trace_id、结构化日志、脱敏、健康检查、指标暴露。
10. 对代码规模与复用检查：DR-1~DR-6，扫描重复代码，核对活账本。
11. 输出问题清单、优先级、修复建议、验证方法、回归测试建议，最终输出审计票。

## §5 七轮分审计划

| 轮次 | 聚焦域 | 输出物 |
|:-----|:-------|:-------|
| 1 | 项目理解 + 审查计划 + 缺失文件 + 风险点 | 计划文档 |
| 2 | 需求功能覆盖矩阵 + 接口契约一致性 | 矩阵 1 + 矩阵 2 |
| 3 | 资产状态机 + 核心业务流程 + CT-3 | 矩阵 3 |
| 4 | 权限、行级隔离、安全 SC-1~SC-8、审计留痕 | 矩阵 4 |
| 5 | 事务、并发、通知、可观测性 OC-1~OC-7 | 问题清单 |
| 6 | 测试覆盖 CT-1~CT-6、DRY DR-1~DR-6、代码质量门禁 | 矩阵 5 + 问题清单 |
| 7 | 规范符合性 + 总结 + 最终审计票 | 审计票 |

用户可在任意轮次要求跳过或合并。

## §6 输出格式

### 6.1 问题表格（每轮输出）

| ID | 严重级别 | 类别 | 文件/行号 | 问题描述 | 证据 | 影响 | 修复建议 | 验证方法 | 关联规则 |
|:---|:---------|:-----|:----------|:---------|:-----|:-----|:---------|:---------|:---------|

**严重级别**：
- **P0**：阻断核心流程、安全漏洞、数据损坏
- **P1**：严重逻辑错误、状态机错误、权限越权、数据不一致
- **P2**：一般功能缺陷、接口不一致、规范偏离、测试缺失
- **P3**：优化建议、可维护性、性能优化

**类别**：功能完整性 / 逻辑完整性 / 接口契约 / 数据模型 / 状态机 / 权限安全 / 事务并发 / 审计留痕 / 通知 / 测试 / 规范 / 前端交互 / 后端分层 / 代码质量 / 可观测性 / AI鲁棒性

### 6.2 五大矩阵（按需输出）

1. **功能覆盖矩阵**：功能点 → 需求来源 → 前端入口 → Store → API → 后端 URL/View → Service → Selector → Model → 测试
2. **接口契约矩阵**：功能 → 前端 API → 方法/路径 → 参数 → 响应 → 后端 View → Serializer → 错误码 → 一致性
3. **状态机覆盖矩阵**：状态转换 → 触发动作 → 权限 → 前端入口 → 后端实现 → 前置条件 → 后置副作用 → 审计 → 通知 → 测试 → CT-3
4. **权限矩阵**：角色 → 资源 → 操作 → 行级隔离规则 → 后端校验 → 前端路由/按钮 → 测试
5. **规则符合性矩阵**：规则 ID → 检查项 → 符合性 → 证据 → 备注（覆盖 CT/DR/SC/OC/AR）

### 6.3 最终审计票

审查完成后，**必须**输出：

```markdown
[审计票 - 必填项]
- 读取规范：已读 [后端/前端] AGENTS & Rules
- CT-1[√] CT-3[√] CT-5[√] — 核心测试覆盖 / 状态机全路径 / 测试失败阻塞
- DR-1[√] DR-5[√/豁免] — 业务逻辑唯一实现 / 文件规模（存量豁免标记）
- SC-1[√] SC-3[√] — 密钥硬编码禁止 / SQL 注入防护
- 跨端契约：未破坏
- 红线触发：无 / [HALT]已确认
- 建议提交：是 / 否

[审计票 - 自检项]
- 测试：CT-2[√] CT-4[√] CT-6[√]
- DRY：DR-2[√] DR-3[√] DR-4[√] DR-6[√]
- 安全：SC-2[√] SC-4~SC-8[√]
- 可观测性：OC-1~OC-3[√] OC-4[~] OC-5[~] OC-6[√] OC-7[~]
- AI鲁棒性：AR-1~AR-5[√]
- AI行为：Fact-1[√]（事实基线）
- 写作风格：Style-1~Style-3[√]
- 覆盖率：整体 XX%（≥80%）/ 核心 XX%（≥90%）
```

## §7 约束（继承根级 AGENTS §9）

1. **Fact-1**：只基于用户提供的代码和文档分析，禁止编造不存在的文件、接口或行为。
2. **证据引用**：每个问题必须引用具体文件、行号、代码片段或文档条目。
3. **不确定标注**：不确定的地方标记"需人工确认"，推测性内容标注 `[推测]`（Fact-2）。
4. **不改代码**：修复建议仅作为建议，标注影响范围和风险。
5. **人工确认**：涉及数据库结构变更、敏感配置变更、跨目录修改时，先列出并触发人工确认。
6. **分批审查**：先计划后执行，不要一次性审查所有代码。
7. **区分级别**：区分"确认的问题"和"需人工确认的疑点"。
8. **缺失文件**：关键文件缺失时，先列出需要补充的文件清单，不要继续猜测。
9. **写作风格**：Style-1~Style-3（原创表述、MLA 引用、正式但不晦涩）。
10. **[HALT] 暂停**：触发 [HALT] 时立即暂停，列出需要人工确认的内容。
11. **审计票必出**：审查未输出审计票视为未完成。

## §8 快速模式（用户可选）

用户说"快速审查"或"/code-quality-check fast"时，跳过矩阵输出，仅执行：
- 第 1 轮（计划）+ 第 6 轮（测试+DRY+质量）+ 第 7 轮（审计票）
- 问题表格只报 P0 和 P1
