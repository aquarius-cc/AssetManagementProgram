# 修复登记同步（Resolution → Ledger Sync）

> 目标：代码修复落地后，把同一修复原子地同步到两份登记源——审查报告「修复追踪」与 Bug 活账本 BF 条目，杜绝"修完了代码但文档不登记"的断链，并保证每条登记的**行号引用可复核、验证数据可追溯**（落根级 AGENTS §9 Fact-1 事实基线）。

## 前置事实（开工前必须核实）

1. 本仓库登记源为两处：
   - `docs/Review/full-review-report-<日期>.md`（或近期审查报告）——P0/P1/P2/P3 表 + 「修复追踪」表
   - `docs/BugFixed/Bug修复活账本.md`——BF-XXX 条目，编号唯一、自增
2. 活账本条目强制三要素：证据（文件:行号 / 日志原文）、根因、修复方案 + 验证记录（缺一不通过审核）。
3. 审查报告 P 级行的"已修复"标记约定：问题描述与规则号双双删除线 + `✅ 已修复 <日期>（详见「修复追踪」）`（对照 #1 行的既有先例）。
4. **行号必须以当前工作区为准**：修复会移动行号，登记前用 `rg` 实测，禁止沿用审查报告里的旧行号。

## 工作流

### Step 1 — 定位登记源条目

- 从修复任务反查：审查报告里哪个 `#N` 对应本次修复（按文件、问题描述、规则号匹配）。
- 确认规则号（B7 / M-3 / DR-1 / SC-7 等）与故障描述；BF 活账本是否已存在同题条目（防重号/重复登记）。

### Step 2 — 更新审查报告 P 级行

对命中的 P 级表行执行删除线标记（保持表格列数不变）：

```markdown
| N | ~~`文件:行号`~~ | ~~问题描述~~ ✅ **已修复 2026-09-20**（详见「修复追踪」） | ~~B7~~ |
```

- 行号列（问题定位）与规则号列均划线，表示"已解决"。
- 若审查报告另有「建议修复优先级」「统计」等段落涉及该 #N，视情同步（例如从"待修"表述中移除），但要保守——只改事实，不动统计数字除非明确要求。

### Step 3 — 追加「修复追踪」行

找到「## 修复追踪」表格，在其末尾追加，**每个文件一行**：

```markdown
| N | 2026-09-20 | `<文件>` `<函数/区域>` | <措施：改了什么、为什么> | <验证命令+结果> |
```

- `N` 列与 P 级行号一致；同 N 多文件多行。
- 措施必须写可复现的变更（签名/透传/复用点），验证列写**实际执行的命令与通过结果**，禁止虚空。
- 若本 N 修复改变了对外契约（API 响应结构、端点写字段、schema）→ 在末尾追加 `**#N 验证结果**` 小结行：全量测试数、ruff、mypy（区分"目标文件 0 新增错误"与"存量错误"）、schema 是否需要重导出。

### Step 4 — 活账本 BF 条目（编号自增）

- `BF-` 编号取活账本现有最大号 +1（先 `grep '^## BF-'` 确认，禁止臆测）。
- 标题格式：`## BF-<NNN> 【状态】<一句话标题>（登记来源，如 审查报告 #5 B7）`
- 状态取值：`已关闭` / `待验证` / `降级` / `待核查`；代码级验证通过即 `已关闭`。
- 元信息三行：发现日期（含来源报告）、严重级别（P0~P3）、影响范围（文件清单 + 是否有契约变更）。
- 正文段（对齐 BF-008/BF-012 先例结构）：
  1. `### 一、问题现象`——编号现象清单
  2. `### 二、根因`——表格式：`| # | 环节 | 事实 |`，事实须带文件:行号或证据原文
  3. `### 三、修复方案`——表格式：`| # | 变更 | 文件 |`
  4. `### 四、对抗审核`——自反清单（见 Step 6）
  5. `### 五、验证记录`——`\`\`\`text` 代码块，逐条命令+结果
  6. `### 六、遗留与关联事项`——超范围发现的登记（含 [待确认]/[待决策] 未决项）
  7. 结尾登记人签名：`*登记人：<名> ｜ 状态：<状态>，完成验证，<日期>*`
- 若条目采用「核实结论」式结构（BF-020/021/022/023 先例：一、核实结论；二、修复方案；三、验证记录；四、遗留与关联事项），须满足：
  - 核实结论每条主张附 `file:line` 实证；定性修正显式写 `报告原表述 > 实测事实`。
  - 修复方案按提交/PR 编号、每文件改法、并标注 `[HALT]` 触发与否。
- 「留痕」要点（对齐 BF-032 案型）：complete-patterns 条目链（新增/关闭登记）、决策反转记录、版本日志行（v2.9.x）、快照护栏影响（G-1~G-5 是否受扰）——留痕事实写入「遗留与关联事项」或独立小节。

### Step 5 — grep 验收（硬性门禁）

执行以下核对，全部通过才算登记完成：

```powershell
# ① 行号引用实测：登记里的每个 文件:行号 必须 rg 命中且行号一致
rg -n "<函数名|关键标识>" <登记引用的文件>
# ② BF 编号不重复
rg -n "^## BF-" docs/BugFixed/Bug修复活账本.md
# ③ 审查报告无残留小写 #N（表格外引用）——按需
# ④ 若本次修复改端点：判定是否需要重新导出 schema 基线（见 AGENTS §3）；纯内部逻辑/审计字段增强 → 无需，登记中写明理由
```

### Step 6 — 对抗审核段（自反，必须输出）

登记内容完成后，在 BF 条目「对抗审核」与交付报告中自反以下风险：

- **行号漂移**：登记行号 vs `rg` 实测是否一致（修复会移行）；不一致即改。
- **虚报验证**：验证记录是否全部实际执行过；`未运行` 必须如实标注，禁止写"通过"。
- **扫描对抗点**：修复是否掩盖了更深的独立 bug（如本流程首个样本发现"审计 operator=None 背后端点实测定测 500"）；该类发现必须进「遗留与关联事项」并标注待决策，不静默吞掉。
- **契约影响**：请求/响应形状、跨端契约、schema 基线是否变化；变化则必须联动前后端/重导出。
- **登记遗漏**：同一修复是否还有其他登记点（如活账本已有关联条目、CHANGELOG）。

### Step 7 — 交付（审计票照常输出）

- 输出修复报告 + 对抗审核 + 宿主审计票（按项目 AGENTS 模板），并显式列出本次同步的**两份文档路径与新增块**。
- 若本次属"修复任务后附加同步"，仅需输出【同步清单】+ 审计票自检行，不重复整份修复报告。

## 强制检查项（每笔登记必查四连）

- ① **双向交叉引用**：审查报告`#N`与活账本 BF 条目、台账（complete-patterns）条目三者可互查；登记后反向 `rg` 确认报告行与条目互指成立。
- ② **版本戳一致**：涉及版本日志（如 v2.9.x）时，头部变更记录与底部登记行日期/版本号逐字一致。
- ③ **防同类重复登记**：登记前 `rg` 活账本与台账已有关闭条目，确认同类问题未被重复登记（防 B-21 式重复）；命中即改引用既有条目不新建。
- ④ **历史快照豁免判断**：台账 `## 历史快照` 段内的历史表述默认不改写；本次登记如需触及历史条目，先判断是否适用"已消除标注/归档"豁免，否则不得改写历史原文。

## 项目路径常量

- 活账本：`docs/BugFixed/Bug修复活账本.md`
- 审查报告：`docs/Review/full-review-report-*.md`（或近期报告）
- 重复模式台账：`Rules_Fiels/Duplicate_Codes/complete-patterns.md`
- 回归护栏脚本：`scripts/check_duplicate_invariants.py`

## 反模式（禁止）

- ❌ 沿用审查报告旧行号不实测（修复后行号必漂移）
- ❌ 虚报测试数字/通过态（Fact-1）
- ❌ 得意忘形把文档登记误扩成代码改动（文档任务不改代码）
- ❌ 超越最大 BF 编号臆造新号（must grep，防重号）
- ❌ 静态复制先例模板而不核对字段（先例结构的字段须逐项自检）
- ❌ 登记后不做 grep/差异自审（改动须 diff 自审，含活账本/审查报告）
- ❌ 把超范围的独立 bug 只在聊天里提一句不留痕（必须进「遗留与关联事项」）

## 验证门禁速查（Windows / 仓库根目录）

```powershell
rg -n "^## BF-" docs/BugFixed/Bug修复活账本.md        # 编号唯一
rg -n "已修复" "docs/Review/full-review-report-<日期>.md"   # 标记落位
# 文档 diff 自审：git diff "docs/Review/full-review-report-<日期>.md" docs/BugFixed/Bug修复活账本.md
```
