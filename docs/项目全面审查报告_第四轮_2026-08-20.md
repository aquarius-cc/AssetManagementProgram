## 四、Docker / 部署分析

### 4.1 🔴 阻塞问题

#### BLOCKER-1：`.dockerignore` 排除了 `docker-entrypoint.sh`

`.dockerignore` 第 92 行：
```
docker-entrypoint.sh
```

`Dockerfile` 第 50 行：
```dockerfile
ENTRYPOINT ["sh", "/app/docker-entrypoint.sh"]
```

**结果**：Docker 容器启动即崩溃 — `sh: 1: /app/docker-entrypoint.sh: not found`

**修复**：从 `.dockerignore` 删除 `docker-entrypoint.sh` 条目。

#### BLOCKER-2：Dockerfile CMD 使用 gunicorn（WSGI）

```dockerfile
CMD ["gunicorn", "--bind", "0.0.0.0:8000", "--workers", "4", "--timeout", "120", "config.wsgi:application"]
```

应用使用 `channels`（ASGI）+ WebSocket。gunicorn 仅支持 WSGI，**WebSocket 在 Docker 中不可用**。

**修复**：改用 `daphne` 或 `gunicorn` + `uvicorn.workers.UvicornWorker`。

## 五、安全漏洞与逻辑矛盾

### 5.1 CRITICAL（必须修复）

#### C-1：审批人代签风险

**文件**：`damaged_asset_view.py:151, 170`

```python
approver_jobcode = request.data.get("approver_jobcode") or request.user.auth_username
```

`approve` 和 `reject` 操作接受客户端传入的 `approver_jobcode`，仅在缺失时回退到当前用户。恶意用户可传入他人 jobcode 伪造审批身份。

**违反规则**：backend-business-rules.md §4.5 — "approver 的 approver 强制 = 当前审批人（后端覆盖传入值，防代签）"

**修复方案**：
```python
approver_jobcode = request.user.auth_username  # 强制使用当前用户
```

#### C-2：RBAC 数据隔离缺口

**文件**：`out_asset_view.py:162`

```python
queryset = OutAssetSelector.get_recyclable_outassets(filters if filters else None)
```

`recyclable` action 绕过 `get_queryset()`（应用 RBAC 行级过滤），直接调用 selector 且不传 `user` 参数。任意认证用户可查看全量可回收资产。

**修复方案**：传入 `user=request.user`，或路由通过 `get_queryset()`。

#### C-3：状态机与文档矛盾

**文档**（`backend-business-rules.md:77`）：`in_use → damaged` 是合法转换（在用状态申请报废）。

**代码**（`state_machine/core.py:155-159`）：`_TRANSITIONS[IN_USE]` 仅包含 `RECYCLED_PENDING`、`BROKEN`、`LOST`，**不含 `DAMAGED`**。

**影响**：从 `in_use` 直接转 `damaged` 会抛出 `InvalidTransitionError`。文档与实现不一致。

**修复方案**：二选一 — ① 在 FSM 中添加 `DAMAGED` 转换；② 更新文档说明正确路径为 `in_use → recycle → recycled_pending → damaged`。
