## 二、CRITICAL（阻塞级，3 项）

### C-1 [CRITICAL] `AssetOperationLogListSerializer` 不存在 — status_log 端点运行时崩溃

- **文件：** `asset_management_backend/apps/assetmanagement/views/asset_view.py:478`
- **证据：** `status_log` action（line 474）执行 `from apps.assetmanagement.serializers import AssetOperationLogListSerializer`，该类在代码库中不存在。仅存在 `AssetOperationLogSerializer`（定义于 `asset_crud_serializers.py:356`）。
- **影响：** `GET /api/v1/assets/{recordcode}/logs/` 端点在运行时抛出 `ImportError`，完全不可用。
- **修复建议：** 将 import 改为 `AssetOperationLogSerializer`，或新建 `AssetOperationLogListSerializer`。

### C-2 [CRITICAL] `WasteAssetViewSet.by_date_range` 绕过 RBAC 行级安全

- **文件：** `asset_management_backend/apps/assetmanagement/views/waste_asset_view.py:170`
- **证据：** Line 170 使用 `WasteAsset.objects.with_asset_details().all()` 直接查询，绕过 `WasteAssetSelector.get_queryset_for_user()` 的部门级数据隔离。
- **影响：** 任何已认证用户可查询全部报废资产记录，无论其所属部门。数据泄露。
- **修复建议：** 改为 `self.get_queryset()` 或调用 Selector 的用户范围过滤方法。

### C-3 [CRITICAL] 前端路由守卫 `roleWhitelist` 对动态路由路径永远匹配不上

- **文件：** `vue-assetmanagement/src/router/guards.ts:44-55`
- **证据：** `roleWhitelist` 定义前缀如 `/assets/recycle`、`/assets/repair`、`/assets/scrap`，但实际路由路径为 `/assets/:code/recycle`、`/assets/:code/repair`（含动态 `:code` 段）。守卫使用 `targetPath.startsWith(prefix)` 匹配，`/assets/ASSET-001/recycle` 永远不会匹配 `/assets/recycle`。
- **影响：** 所有资产操作页面（回收/维修/报废/遗失/找回/标记损坏）的前端 RBAC 守卫完全失效。任何登录用户均可访问这些页面。
- **修复建议：** 将 `roleWhitelist` 前缀改为 `/assets/` 并在值中检查角色，或改用正则匹配。

## 三、MAJOR（重要级，7 项）

### M-1 [MAJOR] `DamagedAssetViewSet.get_queryset` 非 list 路径绕过 RBAC

- **文件：** `asset_management_backend/apps/assetmanagement/views/damaged_asset_view.py:97`
- **证据：** 对非 list action（retrieve、update、approve、reject 等），`get_queryset` 返回 `DamagedAsset.objects.with_asset_details().filter(is_deleted=False)`，未调用 `DamagedAssetSelector.get_queryset_for_user()`。
- **影响：** 任何用户可通过 recordcode 访问任意报废资产记录，绕过部门级 RBAC。
- **修复建议：** 非 list 路径也应通过 Selector 获取用户范围过滤后的 QuerySet。

### M-2 [MAJOR] `StorageViewSet.statistics` 统计包含已软删记录

- **文件：** `asset_management_backend/apps/assetmanagement/views/storage_view.py:67`
- **证据：** `statistics` action 使用 `self.queryset`（`Storage.objects.all()`，line 36），未过滤 `is_deleted=False`。`get_queryset()` 方法正确过滤了软删记录，但 `statistics` 绕过了它。
- **影响：** 统计数据虚高，包含已删除的仓库记录。
- **修复建议：** `statistics` 应使用 `self.get_queryset()` 而非 `self.queryset`。

### M-3 [MAJOR] 多个 View 的 destroy/batch_delete 未传 operator 上下文

- **文件：** `storage_view.py:77-96`、`contract_view.py:93-112`、`asset_type_view.py:67-86`
- **证据：** 这些删除操作调用 Service 方法时未传递 `operator_jobcode` 或 `operator_name`，导致操作日志中缺失操作人信息。对比 `AssetViewSet.destroy`（line 158-166）正确传递了 operator 字段。
- **影响：** 审计日志不完整，无法追溯谁执行了删除操作。
- **修复建议：** 所有 destroy/batch_delete 方法应从 `request.user` 获取 operator 信息并传递给 Service。

### M-4 [MAJOR] `public_scan_view.py` 直接查询绕过 Selector 层

- **文件：** `asset_management_backend/apps/assetmanagement/views/public_scan_view.py:36-40`
- **证据：** 直接使用 `Asset.objects.select_related(...).get(...)` 而非 `AssetSelector`。虽然是公开端点（无需 RBAC），但违反了 BR-1 架构分层规则。
- **影响：** 若 Selector 层逻辑变更（如增加字段、修改过滤），此端点不会同步。
- **修复建议：** 创建或复用 Selector 方法封装查询逻辑。

### M-5 [MAJOR] `RecycleAssetService.create_recycle_asset` 三分支代码高度重复（DR-1）

- **文件：** `asset_management_backend/apps/assetmanagement/services/recycle_asset_service.py:100-232`
- **证据：** is_broken、is_lost、normal 三个分支共享约 70% 相同代码（FSM 调用 + 字段清除 + save + 审计日志）。唯一区别是回收后执行的附加操作。
- **影响：** 违反 DR-1（相同业务逻辑在三处独立实现），维护风险高。
- **修复建议：** 提取公共回收流程为内部方法，仅在 post-recycle 步骤分叉。

### M-6 [MAJOR] 前端 `requiredMinRole` meta 已定义但守卫从未读取

- **文件：** `vue-assetmanagement/src/router/index.ts:621-681`
- **证据：** 7 个独立路由定义了 `meta.requiredMinRole: 'asset_admin'`，类型声明于 `types/vue-router.d.ts`，但 `guards.ts` 实现中从未读取 `to.meta.requiredMinRole`——仅使用 `roleWhitelist` 映射。
- **影响：** 形同虚设的 RBAC 声明，给人虚假的安全感。
- **修复建议：** 在 `guards.ts` 中增加对 `requiredMinRole` 的读取和校验逻辑。

### M-7 [MAJOR] 前端审批状态辅助函数在两个文件中重复实现（DR-1）

- **文件：** `DamagedAssetDetails.vue:145-176`、`DamagedAssetBasicDetails.vue:123-149`
- **证据：** `getApprovalStatusTagType()` 和 `getApprovalStatusText()` 在两个 Vue 文件中本地实现，逻辑与 `utils/statusMapping.ts` 中已有的同名函数完全相同。
- **影响：** 违反 DR-1（同一业务逻辑在三处实现），修改审批状态样式时需同步三处。
- **修复建议：** 删除本地实现，统一从 `statusMapping.ts` 导入。
