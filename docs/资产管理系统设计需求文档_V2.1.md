## 1. 引言

### 1.1 项目背景
随着企业资产规模扩大，传统的手工台账或简单电子表格已无法满足高效、准确、合规的管理需求。本系统旨在构建一套覆盖资产全生命周期的数字化管理平台，实现资产从入库、领用、使用、维修、报废到处置的全程可追溯、可审计、可管控。

### 1.2 目标
1. 建立统一的资产数据中心，实现"账实相符"。
2. 实现资产状态的实时监控与智能预警。
3. 规范资产流转流程，降低资产遗失、损坏风险。
4. 提供完整的审计留痕，满足内外部合规要求。
5. 支持未登记资产的发现与处理，弥补管理盲区。

### 1.3 适用范围
本系统适用于企业内所有固定资产、低值易耗品、IT设备、办公设备等的全生命周期管理，涵盖财务、行政、IT、生产等多个部门。

## 2. 总体说明

### 2.1 系统架构
系统采用前后端分离架构：
- **后端**：Django REST Framework + PostgreSQL，提供RESTful API。
- **前端**：Vue 3 + Element Plus，提供用户交互界面。
- **认证**：JWT（SimpleJWT）实现身份认证与授权。
- **权限**：基于RBAC模型，支持行级数据隔离。

**API版本管理**：所有接口统一使用 `/api/v1/` 前缀，后续版本升级通过版本号区分。

**RBAC权限矩阵**：

| 角色 | 资产出入库 | 报废审批 | 未登记资产处理 | 系统配置 | 审计日志查看 |
|------|-----------|---------|---------------|---------|-------------|
| 系统管理员 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 部门经理 | ✅（本部门） | ✅（本部门） | ✅（本部门） | ❌ | ❌ |
| 资产管理员 | ✅ | ❌ | ❌ | ❌ | ❌ |
| 普通用户 | 查看（本部门） | ❌ | ❌ | ❌ | ❌ |
| 审计员 | ❌ | ❌ | ❌ | ❌ | ✅ |

**行级数据隔离规则**：
- 非管理员角色仅能查看本部门资产
- 通过DRF Permission + QuerySet Filter实现
- 部门层级关系由Department.parent_code字段维护

### 2.2 核心概念
- **资产（Asset）**：企业拥有的具有经济价值的实物或无形资产，每个资产拥有唯一的资产编码（asset_code）和系统内部编码（recordcode）。
- **资产状态（Asset State）**：资产当前所处的生命周期阶段，是业务操作的核心依据。
- **资产属性（Attribute）**：描述资产固有特征，如品牌、规格、使用性质、物理成色等。
- **资产操作记录（Transaction Log）**：记录资产每一次业务动作（出库、回收、状态变更等），形成不可篡改的审计链条。

## 3. 功能模块

| 模块名称 | 功能描述 |
|---------|---------|
| 资产管理 | 资产信息的增删改查、详情查看、盘点、状态变更查询 |
| 出库管理 | 资产领用/借用出库，记录使用人、保管人、使用地点、预计归还日期 |
| 回收管理 | 资产归还回库，支持正常回收、损坏回收、遗失回收，关联出库记录 |
| 损坏管理 | 标记资产损坏，记录损坏原因、描述，直接生效无需审批 |
| 遗失管理 | 标记资产遗失，记录遗失原因、最后位置，直接生效无需审批 |
| 找回管理 | 登记遗失资产的找回，恢复资产状态 |
| **维修管理** | **登记资产维修记录，跟踪维修过程，更新维修后物理成色** |
| 待报废管理 | 提交资产报废申请，进入审批流程（待审批→已批准/已拒绝） |
| 已报废管理 | 审批通过后正式报废，资产退出生命周期 |
| 未登记资产管理 | 处理实物有系统无、系统有无出库、状态异常三种场景，经审批后生成对应记录 |
| 状态变更日志 | 记录资产每一次状态变更的详细历史，供审计追溯 |
| 用户与权限 | 用户管理、部门管理、角色权限控制 |

## 4. 数据模型详细设计

### 4.0 外键删除策略

| 模型 | 外键字段 | on_delete策略 | 说明 |
|------|---------|---------------|------|
| Asset | asset_type_recordcode | PROTECT | 防止删除被引用的资产类型 |
| Asset | asset_contract_recordcode | SET_NULL | 合同删除后置空 |
| Asset | asset_storage_recordcode | PROTECT | 防止删除被引用的仓库 |
| Asset | asset_entry_person_recordcode | SET_NULL | 入库人删除后置空 |
| Asset | asset_applicant_recordcode | SET_NULL | 申请人删除后置空 |
| Asset | asset_manager_recordcode | SET_NULL | 保管人删除后置空 |
| OutAsset | asset_recordcode | PROTECT | 防止删除有出库记录的资产 |
| RecycleAsset | asset_recordcode | PROTECT | 防止删除有回收记录的资产 |
| RecycleAsset | operator_employee | SET_NULL | 操作人删除后置空 |
| BrokenAsset | asset_recordcode | PROTECT | 防止删除有损坏记录的资产 |
| LostAsset | asset_recordcode | PROTECT | 防止删除有遗失记录的资产 |
| DamagedAsset | asset_recordcode | PROTECT | 防止删除有待报废记录的资产 |
| DamagedAsset | approver | SET_NULL | 审批人删除后置空 |
| RepairAsset | asset_recordcode | PROTECT | 防止删除有维修记录的资产 |

> **策略说明**：
> - `PROTECT`：阻止删除被引用的记录，抛出ProtectedError
> - `SET_NULL`：删除被引用记录后，外键置为NULL（仅限nullable字段）
> - `DO_NOTHING`：不推荐使用，可能导致悬挂外键

| 字段名 | 类型 | 必填 | 说明 |
|-------|------|------|------|
| recordcode | Char(32) | 是 | 系统生成的全局唯一编码，用于外键引用 |

| asset_unit | Char(50) | 否 | 计量单位（台/套/个） |
| asset_brand | Char(100) | 否 | 品牌 |
| asset_specification | Char(100) | 否 | 规格型号 |
| asset_type_recordcode | FK(AssetType) | 是 | 资产类型（通过recordcode关联） |
| asset_contract_recordcode | FK(Contract) | 否 | 采购合同 |
| asset_purchase_date | Date | 是 | 购买日期 |
| asset_warranty_period | Integer | 否 | 保修期（年），默认为0 |
| asset_entry_date | Date | 是 | 入库日期 |
| asset_storage_recordcode | FK(Storage) | 否 | 当前所在仓库 |
| asset_entry_person_recordcode | FK(Employee) | 否 | 入库人员 |

| asset_manager_recordcode | FK(Employee) | 否 | 当前保管人 |
| asset_using_location | Char(100) | 否 | 使用地点 |
| asset_current_status | Char(20) | 是 | 当前状态，见状态枚举 |
| usage_type | Char(20) | 是 | 使用性质：new(全新)/used(二手)/refurbished(翻新)，首次出库时锁定 |
| physical_grade | Char(20) | 是 | 物理成色：excellent/good/fair/poor，回收或维修后更新 |
| asset_description | Text | 否 | 补充说明 |
| version | Integer | 是 | 乐观锁版本号，默认为1 |
| is_deleted | Boolean | 是 | 软删除标记 |
| created_at | DateTime | 是 | 创建时间 |
| updated_at | DateTime | 是 | 更新时间 |

**说明**：
- `usage_type` 和 `physical_grade` 为新增字段，用于解决"区分新旧设备"的业务需求。
- `usage_type` 在首次出库时锁定，后续出库不再变更。
- `physical_grade` 在回收或维修完成后更新，反映设备当前物理状态。

### 4.2 出库记录（OutAsset）

| 字段名 | 类型 | 必填 | 说明 |
|-------|------|------|------|
| recordcode | Char(32) | 是 | 系统生成唯一编码 |
| asset_recordcode | FK(Asset) | 是 | 出库资产（可一对多，此处为单资产出库） |
| outasset_number | Integer | 是 | 出库数量，默认为1 |
| outasset_previous_status | Char(50) | 否 | 出库前资产状态（in_store 或 recycled_pending），用于取消出库回退 |
| return_date | Date | 否 | 预计归还日期（借用时填写） |
| outasset_date | Date | 是 | 出库日期，默认当天 |
| outasset_type | Char(50) | 否 | 出库类型：receive(领用)/borrow(借用) |
| outasset_description | Text | 否 | 补充说明 |
| outasset_applicant_recordcode | FK(Employee) | 否 | 出库申请人（出库时填写） |
| outasset_manager_recordcode | FK(Employee) | 否 | 出库保管人 |
| outasset_using_location | Char(100) | 否 | 出库时使用地点 |
| outasset_snapshot | JSON | 否 | 快照，保存出库时的申请人、保管人等关键信息，用于历史追溯 |
| version | Integer | 是 | 乐观锁版本号 |

**业务规则**：
1. 出库时资产状态必须为 `in_store` 或 `recycled_pending`。
2. 出库后资产状态自动变为 `in_use`。
3. 若为首次出库，`usage_type` 自动设为 `new`；否则保持原值。
4. 取消出库时，资产状态恢复为 `outasset_previous_status`。

### 4.3 回收记录（RecycleAsset）

| 字段名 | 类型 | 必填 | 说明 |
|-------|------|------|------|
| recordcode | Char(32) | 是 | 系统生成唯一编码 |
| outasset_recordcode | OneToOne(OutAsset) | 是 | 关联的出库记录 |
| asset_recordcode | FK(Asset) | 是 | 回收资产 |
| recycle_asset_number | Integer | 是 | 回收数量，默认为1 |
| operator_employee | FK(Employee) | 否 | 回收操作人 |
| recycle_type | Char(50) | 否 | 回收类型（正常/损坏/遗失等） |
| recycle_asset_date | Date | 是 | 回收日期 |
| recycle_asset_description | Text | 否 | 补充说明 |
| is_broken | Boolean | 否 | 是否损坏回收（已废弃，由关联记录判断） |
| is_lost | Boolean | 否 | 是否遗失回收（已废弃） |
| version | Integer | 是 | 乐观锁版本号 |

**业务规则**：
1. 回收时资产状态必须为 `in_use`。
2. 回收后资产状态变为 `recycled_pending`。
3. **若回收时发现损坏，必须同时创建 BrokenAsset 记录；若发现遗失，必须创建 LostAsset 记录。**
4. 取消回收时，资产状态恢复为 `in_use`。

### 4.4 损坏记录（BrokenAsset）

| 字段名 | 类型 | 必填 | 说明 |
|-------|------|------|------|
| recordcode | Char(32) | 是 | 系统生成唯一编码 |
| asset_recordcode | FK(Asset) | 是 | 损坏资产（一对多，允许同一资产多次损坏） |
| broken_date | Date | 是 | 损坏日期，默认当天 |
| operator_employee | FK(Employee) | 否 | 操作人 |
| broken_reason | Char(100) | 是 | 损坏原因 |
| broken_description | Text | 否 | 详细描述 |
| version | Integer | 是 | 乐观锁版本号 |

**业务规则**：
1. 资产可在 `in_store`、`in_use`、`recycled_pending` 状态下标记损坏。
2. 标记损坏后资产状态变为 `broken`。
3. 损坏资产可送修（创建维修记录，进入 `repairing` 状态）或申请报废（进入 `damaged` 状态）。

| lost_description | Text | 否 | 详细描述 |
| version | Integer | 是 | 乐观锁版本号 |

**业务规则**：

### 4.7 维修记录（RepairAsset）【新增】

| 字段名 | 类型 | 必填 | 说明 |
|-------|------|------|------|
| recordcode | Char(32) | 是 | 系统生成唯一编码 |
| asset_recordcode | FK(Asset) | 是 | 维修资产（一对多，允许同一资产多次维修） |
| repair_date | Date | 是 | 送修日期，默认当天 |
| expected_return_date | Date | 否 | 预计完成日期 |
| actual_return_date | Date | 否 | 实际完成日期 |
| repair_status | Char(20) | 是 | 维修状态：in_progress(维修中)/completed(已完成)/failed(维修失败) |
| repair_reason | Char(100) | 是 | 维修原因 |
| repair_description | Text | 否 | 维修详细描述 |
| repair_cost | Decimal(10,2) | 否 | 维修费用 |
| physical_grade_before | Char(20) | 否 | 维修前物理成色 |
| physical_grade_after | Char(20) | 否 | 维修后物理成色 |
| operator_employee | FK(Employee) | 否 | 维修操作人 |
| version | Integer | 是 | 乐观锁版本号 |

**业务规则**：
1. 资产在 `broken` 状态下可创建维修记录，同时资产状态变为 `repairing`。
2. 维修完成后，`repair_status` 设为 `completed`，资产状态变为 `in_store`，并更新 `physical_grade`。
3. 维修失败时，`repair_status` 设为 `failed`，资产状态变为 `damaged`（可申请报废）。
4. 维修记录与资产物理成色联动：维修完成时，必须更新资产的 `physical_grade` 为维修后成色。

### 4.8 待报废记录（DamagedAsset）

| 字段名 | 类型 | 必填 | 说明 |
|-------|------|------|------|
| recordcode | Char(32) | 是 | 系统生成唯一编码 |
| asset_recordcode | OneToOne(Asset) | 是 | 待报废资产（一个资产只能有一条待报废记录） |
| damaged_asset_number | Integer | 是 | 待报废数量，默认为1 |
| damaged_date | Date | 是 | 申请日期，默认当天 |
| approval_status | Char(20) | 是 | 审批状态：pending/approved/rejected |
| approver | FK(Employee) | 否 | 审批人 |
| damaged_asset_description | Text | 否 | 报废原因说明 |
| original_status | Char(20) | 否 | 进入待报废前的原状态（用于审批拒绝时回退） |
| version | Integer | 是 | 乐观锁版本号 |

**业务规则**：
1. 资产在 `broken`、`lost`、`in_use`、`recycled_pending` 状态下均可提交报废申请。
2. 提交后资产状态变为 `damaged`，同时记录 `original_status`。
3. 审批通过后，资产状态变为 `scrapped`（终态），并创建 WasteAsset 记录。
4. 审批拒绝后，资产状态恢复为 `original_status`（broken/lost/recycled_pending等）。

| unregistered_asset_storage | FK(Storage) | 否 | 目标仓库 |
| handle_description | Text | 否 | 处理说明 |
| approval_status | Char(20) | 是 | 审批状态：pending/approved/rejected |
| approver | FK(Employee) | 否 | 审批人 |
| approval_date | Date | 否 | 审批日期 |
| approval_remark | Text | 否 | 审批备注 |
| result_asset | FK(Asset) | 否 | 结果资产（处理完成后创建） |
| result_recycle_asset | FK(RecycleAsset) | 否 | 结果回收记录 |
| result_damaged_asset | FK(DamagedAsset) | 否 | 结果待报废记录 |
| attachments | JSON | 否 | 附件列表（文件路径数组） |
| version | Integer | 是 | 乐观锁版本号 |

**业务规则**：
1. 审批通过后根据 `handle_type` 执行对应处理：
   - `create_and_recycle`：新建资产并直接设置为 `recycled_pending`，并创建回收记录。
   - `create_and_damaged`：新建资产并直接设置为 `damaged`，并创建待报废记录。
   - `supplement_and_recycle`：补建出库记录后立即回收。
   - `correct_and_recycle`：修正资产状态后回收。
2. 审批拒绝则流程结束。
3. 只有待审批状态的记录允许修改和删除。

## 5. 状态机设计

### 5.1 状态定义

| 状态代码 | 状态名称 | 说明 | 是否终态 |
|---------|---------|------|---------|
| in_store | 在库 | 资产在仓库中，未分配使用 | 否 |
| in_use | 在用 | 资产已被领用/借用，正在使用中 | 否 |
| recycled_pending | 已回收待发放 | 资产已回收，等待下次分配 | 否 |
| broken | 已损坏 | 资产存在但已损坏 | 否 |
| **repairing** | **维修中** | **资产正在维修（需创建维修记录）** | **否** |
| lost | 已遗失 | 资产无法找到 | 否 |
| damaged | 待报废 | 资产损坏/遗失，等待报废审批 | 否 |
| scrapped | 已报废 | 审批通过，资产退出生命周期（终态） | **是** |

**说明**：
- `repairing` 状态为新增，用于跟踪资产维修过程。进入该状态必须同时创建 `RepairAsset` 维修记录。
- 维修完成或失败后，资产状态将自动流转至 `in_store` 或 `damaged`。

### 5.2 状态转换规则

| 当前状态 → 目标状态 | 转换方法 | 触发业务 |
|-------------------|---------|---------|
| in_store → in_use | outasset() | 出库（首次） |
| in_store → broken | mark_broken() | 标记损坏（在库损坏） |
| in_store → lost | mark_lost() | 标记遗失（在库遗失） |
| in_use → recycled_pending | recycle() | 回收 |
| in_use → damaged | damaged() | 申请报废（在用） |
| recycled_pending → in_use | outasset() | 再次出库 |
| recycled_pending → broken | mark_broken() | 标记损坏 |
| recycled_pending → lost | mark_lost() | 标记遗失 |
| recycled_pending → damaged | damaged() | 申请报废（待发放） |
| broken → **repairing** | **start_repair()** | **送修（必须创建维修记录）** |
| broken → damaged | damaged() | 申请报废（损坏） |
| **repairing → in_store** | **repair_done()** | **维修完成回库（更新physical_grade）** |
| **repairing → damaged** | **repair_failed()** | **维修失败报废** |
| lost → in_store | found_and_return() | 找回 |
| lost → damaged | damaged() | 申请报废（遗失） |
| damaged → scrapped | approve() | 审批通过 |
| damaged → recycled_pending | reject() / cancel_damaged() | 审批拒绝或用户取消 |
| damaged → broken | reject_to_broken() | 审批拒绝（原状态为broken） |
| damaged → lost | reject_to_lost() | 审批拒绝（原状态为lost） |

**特殊回退操作（不在常规转换表中）**：

| 当前状态 → 目标状态 | 方法 | 说明 |
|-------------------|------|------|
| in_use → in_store/recycled_pending | cancel_outasset(previous_status) | 取消出库，根据出库前状态回退 |
| recycled_pending → in_use | cancel_recycle() | 取消回收，恢复到在用 |
| 任意非终态 → recycled_pending | force_recycle_from_any() | 强制回收（管理员特殊操作） |

### 5.3 状态机职责划分

**状态机（AssetFSM）**：
- 仅负责修改 `asset.asset_current_status` 字段。
- 提供显式的转换方法，每个方法内部校验合法性。
- 不处理事务、并发锁、其他字段更新、日志记录。

**Service层**：
- 控制事务边界（`@transaction.atomic`）。
- 使用 `select_for_update()` 实现行级锁，防止并发冲突。
- 调用状态机方法后，保存资产实例。
- 负责创建关联业务记录（OutAsset、RecycleAsset、RepairAsset等）。
- 负责创建状态变更日志（AssetStateLog）。

## 6. 业务流程详细说明

### 6.1 资产入库流程
1. 采购到货后，管理员在系统录入资产信息（资产编码、名称、品牌、规格、购买价格、购买日期、入库日期、仓库等）。
2. 系统自动生成 `recordcode` 并分配 `asset_code`（若未提供）。
3. 资产状态默认为 `in_store`，`usage_type` 默认为 `new`，`physical_grade` 默认为 `good`。
4. 保存资产主表记录，并关联入库人员。

### 6.2 资产出库流程
**前置条件**：资产状态为 `in_store` 或 `recycled_pending`。

1. 申请人提出领用/借用申请。
2. 管理员选择资产，填写出库数量、出库类型（领用/借用）、预计归还日期（借用时）、使用地点、保管人等信息。
3. 系统创建 OutAsset 记录，并记录出库前状态（`outasset_previous_status`）。
4. 系统调用 `AssetFSM.outasset(asset)`，将资产状态变为 `in_use`。
5. 若资产当前为 `in_store` 且 `usage_type` 为 `new`，保留 `new`；若为 `recycled_pending`，`usage_type` 保持不变。
6. 更新资产的 `asset_applicant_recordcode`、`asset_manager_recordcode`、`asset_using_location`。
7. 创建状态变更日志。
8. 返回出库单号。

**取消出库**：
- 在出库记录被删除时触发。
- 系统根据 `outasset_previous_status` 调用 `cancel_outasset(asset, previous_status)`，将状态回退。
- 同时清除资产上的保管人、使用地点等信息。

### 6.3 资产回收流程
**前置条件**：资产状态为 `in_use`。

1. 使用人退还资产，管理员接收。
2. 管理员选择对应的出库记录，填写回收日期、回收类型（正常/损坏/遗失）、操作人。
3. 系统创建 RecycleAsset 记录，关联出库记录。
4. 系统调用 `AssetFSM.recycle(asset)`，将资产状态变为 `recycled_pending`。
5. **若回收时发现损坏，必须同时创建 BrokenAsset 记录；若发现遗失，必须创建 LostAsset 记录。**
6. 更新资产的 `asset_manager_recordcode` 为空，`asset_using_location` 清空。
7. 创建状态变更日志。

**取消回收**：
- 删除回收记录时触发，调用 `cancel_recycle()`，状态恢复为 `in_use`。

### 6.4 资产损坏处理流程
**两种途径**：

1. **直接标记损坏**：资产在 `in_store`、`in_use`、`recycled_pending` 状态下，管理员可直接标记损坏，状态变为 `broken`，并创建 BrokenAsset 记录。
2. **回收时发现损坏**：在回收流程中勾选损坏，系统自动创建 BrokenAsset，资产状态变为 `broken`（而非 `recycled_pending`）。

**损坏后操作**：
- **可送修**：创建 RepairAsset 维修记录，调用 `start_repair()`，状态变为 `repairing`。维修完成后调用 `repair_done()`，状态变为 `in_store`，并更新 `physical_grade`。
- **可申请报废**：调用 `damaged()`，进入待报废流程。

### 6.5 资产维修流程【新增】
**前置条件**：资产状态为 `broken`。

1. 管理员创建维修记录（RepairAsset），填写维修原因、预计完成日期等。
2. 系统调用 `AssetFSM.start_repair()`，资产状态变为 `repairing`。
3. 维修过程中，维修记录状态为 `in_progress`。
4. **维修完成**：
   - 管理员更新维修记录，填写实际完成日期、维修费用、维修后物理成色。
   - 系统调用 `AssetFSM.repair_done()`，资产状态变为 `in_store`。
   - 系统更新资产的 `physical_grade` 为维修后成色。
5. **维修失败**：
   - 管理员更新维修记录，状态设为 `failed`。
   - 系统调用 `AssetFSM.repair_failed()`，资产状态变为 `damaged`。
   - 可继续申请报废流程。

### 6.6 资产遗失与找回流程
**遗失标记**：
1. 资产在 `in_store`、`in_use`、`recycled_pending` 状态下可标记遗失。
2. 创建 LostAsset 记录，状态变为 `lost`。

**找回**：
1. 发现资产后，创建 FoundAsset 记录，关联原遗失记录。
2. 调用 `found_and_return()`，状态变为 `in_store`。

### 6.7 资产报废流程（申请→审批→报废）
1. **申请**：资产在 `broken`、`lost`、`in_use`、`recycled_pending` 状态下，管理员提交报废申请。
2. 创建 DamagedAsset 记录，记录原状态（`original_status`），状态变为 `damaged`。
3. 状态变更日志记录。
4. **审批**：审批人查看申请，可选择通过或拒绝。
   - **通过**：调用 `approve()`，状态变为 `scrapped`，创建 WasteAsset 记录，资产退出生命周期。
   - **拒绝**：调用 `reject()`，状态恢复为 `recycled_pending`；或调用 `reject_to_broken()`/`reject_to_lost()` 恢复到原损坏/遗失状态。
5. **取消申请（用户主动取消）**：调用 `cancel_damaged()`，状态变为 `recycled_pending`。

### 6.8 未登记资产处理流程（S1/S2/S3）
**通用步骤**：
1. 发现人在现场发现不在账资产，录入发现信息（名称、品牌、规格、发现地点、发现日期、预估价值等），选择场景类型。
2. 系统生成 `unregistered_code`，状态为 `pending`，提交审批。
3. 审批人查看，选择处理方式（根据场景）：
   - S1（实物有系统无）：处理方式为 `create_and_recycle`（新建资产并回收）或 `create_and_damaged`（新建资产并报废）。
   - S2（系统有无出库）：处理方式为 `supplement_and_recycle`（补建出库记录并回收）。
   - S3（状态异常）：处理方式为 `correct_and_recycle`（修正状态并回收）。
4. 审批通过后，系统执行对应操作：
   - S1-create_and_recycle：创建新资产，调用 `unregistered_create_and_recycle()` 直接设置状态为 `recycled_pending`，并创建 RecycleAsset 记录。
   - S1-create_and_damaged：创建新资产，调用 `unregistered_create_and_damaged()` 直接设置状态为 `damaged`，并创建 DamagedAsset 记录。
   - S2：补建一条 OutAsset 记录（出库日期为历史日期），然后立即创建 RecycleAsset 进行回收。
   - S3：直接调用 `force_recycle_from_any()` 强制将资产状态置为 `recycled_pending`，并创建回收记录。
5. 记录处理结果（`result_asset`、`result_recycle_asset`、`result_damaged_asset`）。
6. 审批拒绝则不做任何处理，流程结束。

## 7. 业务规则与约束

### 7.1 状态流转合法性
1. 任何状态变更必须通过 `AssetFSM` 提供的转换方法，不可直接修改 `asset_current_status`。
2. 所有转换方法会校验当前状态是否允许转换到目标状态，否则抛出 `InvalidTransitionError`。
3. `scrapped` 为终态，不允许任何转出。

### 7.2 并发控制
1. 使用乐观锁（`version` 字段）防止并发更新冲突。
2. 在涉及状态变更的关键事务中，Service层应使用 `select_for_update()` 对资产行加锁，避免并发问题。
3. **实现建议**：
   - 资产出库、回收、报废等核心操作必须使用悲观锁（`select_for_update()`）。
   - 查询操作使用乐观锁（检查 `version` 字段）。
   - 并发冲突时返回明确的错误信息（如"资产已被其他用户操作，请刷新后重试"）。

### 7.3 事务要求
1. 涉及状态变更的业务操作（出库、回收、报废等）必须在同一个数据库事务中完成。
2. 若事务中任意步骤失败，所有变更回滚，保证数据一致性。
3. **实现建议**：
   - 使用 `@transaction.atomic` 装饰器包裹核心业务方法。
   - 对于复杂流程（如未登记资产处理），使用 `transaction.atomic()` 上下文管理器。

### 7.4 数据一致性
1. 资产主表中的 `asset_current_status` 必须与最新的业务记录（OutAsset、RecycleAsset等）保持一致。
2. 例如，存在未回收的出库记录时，资产状态应为 `in_use`；存在未审批通过的待报废记录时，资产状态应为 `damaged`。
3. **系统应提供定期一致性检查任务，发现异常自动告警**。
4. **实现建议**：
   - 每日定时任务检查数据一致性。
   - 发现不一致时生成告警日志并通知管理员。
   - 提供数据修复工具（需管理员权限）。

### 7.5 软删除策略
1. 所有核心模型继承 `BaseModel`，支持软删除（`is_deleted` 标记）。
2. 删除操作仅标记 `is_deleted=True`，数据保留用于审计。
3. 唯一约束需配合 `condition=models.Q(is_deleted=False)` 实现"仅未删除记录唯一"。

### 7.6 状态变更日志
1. 每次状态变更（包括取消操作）必须记录到 `AssetStateLog`。
2. 日志包含操作人（从当前登录用户获取）、关联单据号（如出库单号）、变更原因（可选）。
3. 日志不可修改或删除，仅提供查询接口。

## 8. 异常处理机制【新增】

### 8.1 状态转换异常
| 异常类型 | 触发条件 | 处理方式 |
|---------|---------|---------|
| `InvalidTransitionError` | 尝试执行非法状态转换 | 返回400错误，提示"当前状态不允许此操作" |
| 并发冲突 | 乐观锁版本不匹配 | 返回409错误，提示"资产已被其他用户操作，请刷新后重试" |
| 资产不存在 | 操作的资产已被删除 | 返回404错误，提示"资产不存在" |

### 8.2 业务流程异常
| 异常场景 | 处理方式 |
|---------|---------|
| **维修过程中资产再次损坏** | 允许创建新的损坏记录，但资产状态保持 `repairing`，维修记录状态更新为 `failed` |
| **找回的资产与原遗失资产不匹配** | 系统提示"找回资产编码与原遗失资产不匹配"，要求人工确认 |
| **出库记录和回收记录不匹配** | 系统提示"回收的出库记录与当前资产不匹配"，禁止操作 |
| **审批人与申请人为同一人** | 系统提示"审批人不能与申请人为同一人"，禁止审批 |
| **批量操作部分失败** | 逐条执行，成功记录继续处理，失败记录返回具体错误信息 |

### 8.3 数据一致性异常
| 异常场景 | 处理方式 |
|---------|---------|
| 资产状态与业务记录不一致 | 定时任务检测，生成告警日志，通知管理员 |
| 维修记录缺失但状态为 `repairing` | 自动将状态回退到 `broken`，记录异常日志 |
| 报废记录缺失但状态为 `damaged` | 保留状态，但标记为异常，禁止进一步操作 |

### 8.4 响应格式规范

**成功响应**：
```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

**错误响应**：
```json
{
  "code": 1001,
  "message": "操作失败",
  "data": {
    "error_type": "InvalidTransitionError",
    "detail": "当前状态(in_use)不允许标记损坏，只有(in_store, recycled_pending)状态可以标记损坏",
    "suggestion": "请先回收资产后再标记损坏"
  }
}
```

**业务错误码定义**：

| 错误码范围 | 含义 | 示例 |
|-----------|------|------|
| 0 | 成功 | - |
| 1000-1999 | 状态流转错误 | 1001: InvalidTransitionError |
| 2000-2999 | 数据校验错误 | 2001: 字段缺失 |
| 3000-3999 | 权限错误 | 3001: 无操作权限 |
| 4000-4999 | 业务规则错误 | 4001: 资产已被占用 |
| 5000-5999 | 系统错误 | 5001: 数据库连接失败 |

> **说明**：HTTP状态码由框架自动处理（200/400/403/404/500），`code`字段使用业务错误码，与B1规范保持一致。

## 9. 非功能需求

### 9.1 性能要求
1. **列表查询**：支持单表数据量达100万条记录时，列表查询响应时间 **< 1秒**。
2. **核心操作**：出库、回收等核心操作响应时间 **< 500ms**。
3. **并发支持**：系统应支持至少100个并发用户同时操作。
4. **数据库索引**：需对常用查询字段建立数据库索引：

**Asset表索引**：
   - `asset_code`（唯一索引）
   - `asset_current_status`（普通索引）
   - `asset_type_recordcode`（外键索引）
   - `asset_storage_recordcode`（外键索引）
   - `asset_manager_recordcode`（外键索引，按保管人查询）
   - `is_deleted`（普通索引，软删除过滤）
   - `created_at`（普通索引，时间范围查询）

**OutAsset表索引**：
   - `asset_recordcode`（外键索引，按资产查出库历史）
   - `outasset_date`（普通索引，时间范围查询）

**RecycleAsset表索引**：
   - `asset_recordcode`（外键索引，按资产查回收历史）

**DamagedAsset表索引**：
   - `approval_status`（普通索引，筛选待审批申请）

**UnregisteredAsset表索引**：
   - `approval_status`（普通索引，筛选待审批记录）

**AssetStateLog表索引**：
   - `asset_recordcode`（外键索引，按资产查状态日志）
   - `created_at`（普通索引，按时间范围查日志）
   - `is_deleted`（普通索引）

### 9.2 安全要求
1. **认证**：所有 API 需经过 JWT 认认，Token 有效期可配置（建议：访问令牌2小时，刷新令牌7天）。
2. **授权**：基于 RBAC 模型，细粒度控制用户对资产的操作权限（如只能查看本部门资产）。
3. **审计**：所有状态变更、关键操作（删除、修改敏感字段）记录日志，日志保留至少7年。
4. **数据脱敏**：财务相关字段（购买价格）仅授权人员可见。
5. **实现建议**：
   - 使用 DRF 的权限类实现细粒度权限控制。
   - 敏感操作（如批量删除、状态变更）需要二次确认。
   - 所有 API 接口添加请求频率限制（如每分钟100次）。

### 9.3 可扩展性
1. 状态机采用集中式设计，新增状态或转换只需修改 `AssetFSM`，不影响其他模块。
2. 业务记录（OutAsset、RecycleAsset 等）与资产主表解耦，便于扩展新业务类型。
3. 支持通过配置实现自定义字段扩展（未来考虑）。

### 9.4 可用性
1. **系统可用性**：99.9%（每月停机时间 < 43分钟）。
2. **数据备份**：每日全量备份，实时增量备份。
3. **故障恢复**：RTO（恢复时间目标）< 1小时，RPO（恢复点目标）< 15分钟。

### 10.9 状态流转图

```
                    ┌──────────────┐
                    │  新增资产     │ (in_store)
                    └──────┬───────┘
                           │ 出库（领用/外借）            回收(is_broken)
                           ▼                              ▼
                    ┌──────────────┐              ┌──────────────┐
                    │  在用资产     │ (in_use)      │  已损坏       │ (broken)
                    └──┬───┬───┬───┘              └──────┬───┬───┘
                       │   │   │ 回收                     │   │ 送修
                       │   │   │ 回收(is_lost)            │   ▼
                       │   │   ▼               ┌──────────────┐   ┌──────────────┐
                       │   │ ┌────────────┐    │  待报废       │   │  维修中       │
                       │   │ │ 已遗失     │    └──┬───────┬───┘   └──────┬───────┘
                       │   │ │ (lost)     │       │       │              │
                       │   │ └──┬────┬────┘       │       │              │ 维修完成
                       │   │    │    │ 找回→in_store│  审批拒绝      │
                       │   │    │    ▼            │  (按original_status)   ▼
                       │   │    │ ┌──────────┐   │              ┌──────────────┐
                       │   │    │ │ 找回记录  │   │              │  在库资产     │
                       │   │    │ │(found)   │   │              │ (in_store)   │
                       │   │    │ └──────────┘   │              └──────────────┘
                       │   │    ▼                ▼
                       │   │ ┌──────────────┐ 审批通过
                       │   │ │ 已回收待发放   │ (recycled_pending)
                       │   │ └──┬───────┬───┘
                       │   │    │       │ 重新发放 → in_use
                       │   │    │       │
                       │   │    ▼       ▼
                       │   └─→ 提交报废申请 → damaged
                       └─────────────→ damaged (直接提交报废)
                                      ▼
                               ┌──────────────┐
                               │  已报废       │ (scrapped) [终态]
                               └──────────────┘
```

**说明**：
- `damaged → recycled_pending` 支持审批拒绝和用户取消两种场景。
- `repairing → in_store` 维修完成时，必须更新资产的 `physical_grade`。
- `repairing → damaged` 维修失败时，可继续申请报废流程。
