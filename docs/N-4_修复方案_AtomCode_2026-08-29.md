## 2. 等价性证明（零逻辑变更，逐条）

1. **兜底删除**：`PERMISSION_CODES.SYSTEM_CONFIG_MANAGE || 'x'` 中，左侧是模块级 `const` 对象上的非空字符串字面量值 → 运行时恒为 truthy → `||` 右侧永不求值。删除右侧，`hasPermission` 收到的实参不变。
2. **字面量 → 常量**：4 处替换均是"把字符串 `'P'` 换成一个值恰为 `'P'` 的 `const` 键"（F1 逐字节核对）。`hasPermission(code: string)` 的实参在运行时逐字节相同 → 短路结构（`:111` 的 `isAdmin.value ||`）与求值顺序不变 → computed 依赖图不变（`PERMISSION_CODES` 是纯常量模块，非响应式对象，不引入新依赖）→ Vue 响应性、菜单可见性、按钮显隐行为不变。
3. **import 新增**（仅 usePermission.ts）：常量文件零 import（F4）→ 无循环依赖；AsideMenu 现状已同时 import 两者（F2）→ 模块图无新边；Vite 产物中该模块已被 AsideMenu 拉入，usePermission 的引用不新增 chunk 内容。
4. **类型**：`PERMISSION_CODES.X` 是 `string`（对象字面量推断），与 `hasPermission` 形参类型一致，`vue-tsc --noEmit` 无新错误。

## 6. 对抗审核自查表

| 攻击点 | 方案回应 |
|---|---|
| "删掉 `\|\|` 兜底会不会在常量缺失时炸？" | 常量缺失（键拼错）时 `PERMISSION_CODES.X` 是 `undefined`，带兜底时**也只有兜底生效、行为反而相同**（`undefined \|\| 'x'` → `'x'`）——兜底防的不是"键缺失"（那时无济于事，会静默 fallback 到字面量掩盖拼写错误），它只防"值为空串/0"。而值是全文件统一生成、逐字节核对过 F1 的非空字面量。删除兜底后若真出现键缺失，`hasPermission(undefined)` 会**响亮失败**（菜单不可见 + 类型层面 vue-tsc 不报错但 A6 验收能抓），比静默 fallback 掩盖问题更安全——这正是 M-6"防退化"的设计意图 |
| "为什么不顺手把 usePermission:111 的 `isAdmin.value \|\|` 冗余前缀删了？" | 行为等价（F7 短路），但删除会扩大 diff 且与本任务语义（字面量迁移）正交；单职责 commit 更易回滚。记为后续可选项 |
| "测试 mock 用字面量、实现用常量，双源不是又回来了？" | 测试 mock 是**契约验证**：它验证"传入字符串 X 的权限时 computed 为真"，这正是后端 my-permissions 通道的契约值，独立于前端如何引用常量是正确解耦；真正的"单一事实来源"约束是 M-6.2/6.3（生成式常量 + CI 词表守卫）的职责，本方案不越界 |
| "RolePermDialog:132 注释里的字面量要不要迁？" | 不迁。注释迁移为 `PERMISSION_CODES.SYSTEM_CONFIG_MANAGE` 会丢失人类可读的权限码原文，降低对照价值；且 A1 验收只查带引号的字符串，注释不命中 |
| "5 行改动 + 1 行 import，值得单独 commit 吗？" | 是。N-4 是独立审查项，独立 commit 可单独 revert；且与第四轮建议的收尾批次（N-8 定性 → N-4 → M-3 → M-6.2/6.3）中 ② 位置对齐，不与后续 CI 改动混在一个变更里 |
