## 2. 目标硬约束（不变量）

1. score ≥ **80.0**（下限门）；
2. score ≥ **83.25676365492598**（基线门，全精度比较）；
3. `mutmut run` 不得出现 "Stopping early"（早停异常见 BF-065）；
4. **`setup.cfg` 的 `source_paths` / `test_selection` 当前值不上线**（扩围生效前双门禁必红，见 §3）。

## 3. 为什么只立项、不改 cfg（核心论证）

- 扩 `source_paths` 加入 `apps/usermanagement/services` 而不动 test_selection 时：usermanagement 的变异体**无任何测试映射**（实测：temp 扩围后 `print-time-estimates` 输出 2085 条 `<no tests>`、0 条有测试映射；该数字受 ~/ 副本 mutants 缓存状态影响，仅作"无映射"证据，不作规模证据）。
- mutmut 评分分母 = killed + survived + no_tests。no_tests 计入分母但不算 killed → 扩围后天一效应：score 分子不变、分母暴增 → **双门禁立即红**（score < 83.25676365492598 且可能 < 80.0）。
- 因此唯一合规路径是方案 A：先为 usermanagement/services 补齐足量测试（目标：usermanagement 域单跑分数 ≥ 基线），再扩配置。

## 4. 实测数据（估算依据）

| 项 | 实测值 |

| mutmut 完整 run 现范围成本 | 未在本轮单测（历史经验约数小时级，Stopping early 探测器 `~/mutmut_start.sh` 备用） |

估算推导（[推测] 基于上述实测外推）：
- 每 killed 判定 ≈ 目标 mutant 触发测试子集的运行时长：worst-case 触及全量双域套件 ≈ 313s；现范围 mutant 典型只触 assetmanagement 子集 ≈ 228s 上限。
- 扩围后新增 mutant 数 ≈ usermanagement/services 函数体规模×~30（现范围 listing 数量级 2.7k 外推）；即使其中仅 1/3 有测试映射且只触新域 85s 子集，预估新增 run 成本 ≈ 数百 mutant × 分钟级 ≈ **数小时至半天**；映射为空的 mutant 若直接计入 no_tests，分数直接被稀释——**这假设成立时双门禁连 240 分钟暂停线都可能碰不到就先红了**。
- 故"估时 >240 分钟即暂停"阈值（冻结方案 §五-4）按 pytest/估算口径执行，留 +20% 缓冲。
