## 一、总体结论

## 二、严重问题（功能失效 / 跨端契约断裂）

### 2.1 [严重] 报废申请页面调用不存在的后端端点（功能 404）

- **证据**：
  - `vue-assetmanagement/src/views/ScrapAssetView.vue:69-73` 提交时调用 `assetAPI.applyDamaged(assetCode.value, { reason })`
  - `vue-assetmanagement/src/api/asset.ts:356-359` `applyDamaged` 请求 `POST /assets/assets/{recordcode}/apply-damaged/`
  - 后端 `AssetViewSet`（`apps/assetmanagement/views/asset_view.py`）**无** `apply_damaged` action，全仓 grep 无该端点
  - 后端报废申请正确端点为 `POST /assets/damaged-assets/`（`damaged_asset_view.py:111` `create`），前端 `src/api/damagedAsset.ts:58-59` 已有正确的 `createDamagedAsset`
- **影响**：`/assets/:code/scrap` 路由（`router/index.ts:684-693`，requiredMinRole: asset_admin）可正常进入，但提交申请必然 404，报废申请功能完全不可用。
- **正确路径已存在但未接线**：`DamagedAssetForm.vue` 走 `useDamagedAssetStore().create`（正确端点），但 `ScrapAssetView.vue` 未复用。
- **修复建议**：`ScrapAssetView.vue` 改为调用 `damagedAssetStore.create`（或 `damagedAssetAPI.createDamagedAsset`），并删除 `asset.ts` 中失效的 `applyDamaged`。

### 2.2 [严重] 资产详情页二维码 URL 双前缀（图片 404）

- **证据**：`BasicAssetDetails.vue:296-297`
  ```ts
  const baseUrl = import.meta.env.VITE_API_BASE_URL || 'http://127.0.0.1:8000'
  qrCodeUrl.value = `${baseUrl}/api/v1/assets/${recordcode}/qr-code-image/`
  ```
  - dev：`VITE_API_BASE_URL=/api/v1` → `/api/v1/api/v1/assets/...`（双前缀）
  - prod：`VITE_API_BASE_URL=http://127.0.0.1:8000/api` → `.../api/api/v1/assets/...`（双前缀）
- **影响**：`<img>` 直接加载（不经 axios），QR 图片必然 404，资产详情页二维码不显示。违反 AC-60e（详情页显示二维码）。
- **修复建议**：URL 改为 `${baseUrl}/assets/${recordcode}/qr-code-image/`（baseUrl 已含 `/api/v1` 或 `/api`）。

### 2.3 [严重] 员工状态枚举前后端不一致（跨端契约断裂）

- **证据**：
  - 后端 `apps/usermanagement/models.py:170`：`EMPLOYEE_STATUS_CHOICES = [("active","在职"),("left","离职"),("retirement","退休")]`
  - 前端 `src/utils/statusMapping.ts:90-92`：`active→在职`、`inactive→离职`、`probation→试用期`
- **影响**：
  - 后端返回 `left`/`retirement` 时，前端 `EMPLOYEE_STATUS_MAP` 无对应项，`StatusTag.vue` fallback 直接显示原始英文枚举（如 "left"），界面不友好。
  - 前端映射的 `probation`（试用期）后端不存在，属失效定义。
- **说明**：根级 AGENTS.md §3 未把员工状态列入跨端契约（仅资产状态），但此属业务数据契约，需根级统筹修复，前后端同步。
- **修复建议**：统一为 `active/left/retirement`，前端映射补 `left`/`retirement`，删除 `inactive`/`probation`。

## 三、主要问题（矛盾 / 不一致）

### 3.1 [主要] 错误码体系三套并存，3001/1001 等常量从未使用

- **证据**：
  - `utils/response_utils.py:19-35` `BusinessCode`（整数码：0/400/401/403/404/409/500 + 1001/1002/1003/3001/4001）
  - `core/constants.py:107-127` `ERROR_CODES`（字符串码：E001-E006 + "2001"/"2002"/"3002"/"4002"/"5001"）——**全仓无引用，死代码**
  - `apps/assetmanagement/services/out_asset_service.py` 直接硬编码 `error_code="2001"`
  - `core/exceptions.py` `PermissionDeniedError`(403) 继承 APIException，经 `custom_exception_handler` 走 DRF 默认 handler 后由 `error_response` 按 status_code 映射 → 返回 `code=403`，**`PERMISSION_DENIED=3001` 从未实际返回**
- **影响**：
  - 前端依赖 HTTP status（`request.ts:285` 按 401 判断、`useOperationGuard.ts:35` 按 403 判断），功能不受影响。
  - 但业务码体系承诺（backend-business-rules v1.7 声称 D-015 引入 ~50 个四位业务码的 BizCode + ERROR_CODE_TO_BIZ + EXCEPTION_TO_ERROR_TYPE）与实际实现完全不符。
  - 违反根级 §3 契约精神（业务码与 HTTP 解耦），且 `error_response` 中 `PERMISSION_DENIED`/`INVALID_TRANSITION` 等业务码无触发路径，属死代码。
- **修复建议**：删除 `core/constants.py` ERROR_CODES 或并入 BusinessCode；在 exception_handler 中为 `PermissionDeniedError`→3001、`InvalidTransitionError`→1001、`ResourceConflictError`→1002 建立映射；同步更新 backend-business-rules.md 变更日志（v1.7 声称的重构实际未落地）。

### 3.2 [主要] dashboard 后端缺失 5 个端点，前端以 PROD fallback 降级

- **证据**：
  - 后端 `dashboard_view.py` 仅 4 个 action：`overview` / `recent_out_assets` / `recent_asset_recordcodes` / `recent_recycle_assets`
  - 前端 `src/api/dashboard.ts` 请求 8 个端点：新增 `trend` / `department_distribution` / `type_distribution` / `expiring_assets` / `maintenance_reminders`（后端无对应实现）
  - 前端 PROD 下对 5 个端点直接返回 `[]`（技术债，dashboard 相关图表在 PROD 为空）
- **影响**：需求（AC 仪表盘相关）未完整实现，前端已规避但属降级。
- **修复建议**：明确是"待开发需求"还是"删除"——若保留需后端补 5 个 action；否则前端移除调用。

### 3.3 [主要] `.env.production` 的 VITE_API_BASE_URL 缺 `/v1`

- **证据**：`.env.production` `VITE_API_BASE_URL=http://127.0.0.1:8000/api`（无 `/v1`），而 `.env.development` 为 `/api/v1`，`.env.production.test` 为 `https://api.mycompany.com/api/v1`。
- **影响**：当前依赖后端 `config/urls.py:126-133` 的 `/api/` 兼容前缀兜底，功能可用，但与规范（统一 `/api/v1`）不一致，且与 2.2 的 QR bug 叠加导致 `.../api/api/v1/`。
- **修复建议**：改为 `http://127.0.0.1:8000/api/v1`，与 dev/test 对齐。

### 3.4 [主要] dashboard `recent_asset_recordcodes` action 复制粘贴调用错误 Selector

- **证据**：`dashboard_view.py:35-41` `recent_asset_recordcodes` 内部调用 `DashboardSelector.get_recent_recycle_assets(limit=limit)`，与其名称（recordcodes）语义不符；`recent_recycle_assets` action（43-50）调用同一方法。
- **影响**：该端点返回数据与预期不符。前端当前未调用 `recent_asset_recordcodes`，影响暂未暴露。
- **修复建议**：改为调用 `get_recent_out_assets`（或按意图实现），补充对应 Selector。
