## 0. 设计总纲

| | 根因 | 修复形态 | 改动面 |
|---|---|---|---|
| **N-2** | 告警规则引用 backup_* 指标，但**无人写入** | 共享卷 textfile 管道：备份脚本 EXIT trap 原子写 `.prom` → node-exporter `--collector.textfile` 暴露 | 1 新脚本 + 3 脚本接入 + Dockerfile 1 行 + 2 个 compose 文件各 2~3 行 |
| **N-3** | 告警规则引用 probe_ssl_* 指标，但 **blackbox 未部署**且配置无 env 注入机制 | 部署 blackbox + **域名渲染边车**（复用项目既有 nginx tpl+envsubst 惯例）+ file_sd probes job + 数据源自活守卫规则 | 1 小镜像（边车）+ 1 新容器 + 2 模板 + prometheus.yml 1 job + 4 新规则 + `.env.example` 补 DOMAIN |

**共同设计原则**（对抗审核基线）：

1. **现有 4 条告警表达式零改动**——expr 是第二轮已审核的目标态，本次只补数据源；新增 4 条守卫规则是独立增量；
2. **可观测管道绝不反噬业务**——状态写入失败只降级（`|| true`，备份照常完成）；探针走 `/health/`（无限流），15s 一次 ≈ 0.07 rps，与登录 5r/m 预算零串扰；
3. **每个新数据源自带"数据源存活"守卫**——N-2/N-3 的病根是"指标 absent 时规则静默休眠"，若修复后仍是静默休眠，等于换个姿势再犯一次。故新增 4 条守卫规则（§3），使"管道断了"本身可告警；
4. **顺序无关部署、独立 commit、可单独回滚**（§4），任一 commit 单独回退均恢复"规则暂时无数据源"的当前既有状态，不引入新风险面。

## 1. N-2 方案：备份可观测 textfile 管道

### 1.1 数据流

```
backup 容器 (root, crond 驱动 3 个日备脚本)
  └─ EXIT trap → backup_status_write $rc
       └─ 原子发布: 同目录 tmp → mv  /data/backup_status/backup_status.prom
                                                            ↑ 命名卷 backup_status_data
node-exporter (ro 挂载同卷 → /textfile, --collector.textfile.directory=/textfile)
  └─ /metrics 暴露 backup_last_success_timestamp / backup_failures_total
Prometheus (node job, 15s) → 现有 BackupOverdue / BackupFailed 激活
```

### 1.2 文件改动清单

**① 新增 `scripts/backup_status.sh`**（被 source，非独立执行）。核心函数全文：

```bash
#!/bin/bash
# backup_status.sh - 备份可观测状态写入（N-2）
# 由 backup.sh / redis_backup.sh / media_backup.sh source 后在 EXIT trap 中调用。
#
# 契约:
#   backup_last_success_timestamp  gauge   最近一次成功备份的 unix 时间戳（失败时保持旧值）
#   backup_failures_total          counter 失败累计，随命名卷持久化，每次失败 +1
#
# 对抗设计点:
#   1. 原子发布: 同目录 tmp 文件 + mv（同文件系统 rename），node-exporter 永不读到半截文件
#   2. 读-改-写加 flock 保护，防长任务跨 30min 与次日任务重叠时的丢失更新
#   3. 显式 umask 022 / 目录 755 / 文件 644: 官方 node-exporter 镜像为 non-root 用户(UID 65534)，
#      世界可读保证可抓取；若运行 root 版本同样兼容
#   4. 整段 best-effort: 状态写入任何失败都不得影响备份主流程（可观测不得反噬业务）
#   5. 文件缺失/损坏 → 按 0 处理: 计数器只少记不误报
#      （PromQL 对 counter 回落按 reset 处理，increase 不产生假阳性）

backup_status_write() {
  _bsw_rc="${1:-1}"
  _bsw_dir="${BACKUP_STATUS_DIR:-/data/backup_status}"
  {
    mkdir -p "$_bsw_dir"
    umask 022
    chmod 755 "$_bsw_dir" 2>/dev/null || true
    # 读-改-写加锁（三个脚本同容器，/tmp 锁即可；拿不到锁则直接写，竞争窗口毫秒级）
    if command -v flock >/dev/null 2>&1; then
      exec 8>/tmp/backup_status.lock
      flock -w 15 8 || true
    fi
    local f="$_bsw_dir/backup_status.prom" now old_ts=0 old_fail=0 ts fail tmp
    now=$(date +%s)
    if [ -f "$f" ]; then
      old_ts=$(awk   '$1=="backup_last_success_timestamp"{v=$2} END{print v+0}' "$f" 2>/dev/null)
      old_fail=$(awk '$1=="backup_failures_total"{v=$2} END{print v+0}' "$f" 2>/dev/null)
    fi
    case "$old_ts"   in ''|*[!0-9]*) old_ts=0;;   esac
    case "$old_fail" in ''|*[!0-9]*) old_fail=0;; esac
    if [ "$_bsw_rc" -eq 0 ]; then ts=$now; fail=$old_fail; else ts=$old_ts; fail=$((old_fail+1)); fi
    tmp="$_bsw_dir/.backup_status.prom.$$"
    {
      echo "# HELP backup_last_success_timestamp Last successful daily backup run (unix timestamp)."
      echo "# TYPE backup_last_success_timestamp gauge"
      echo "backup_last_success_timestamp $ts"
      echo "# HELP backup_failures_total Total failed daily backup runs (monotonic since volume creation)."
      echo "# TYPE backup_failures_total counter"
      echo "backup_failures_total $fail"
    } > "$tmp"
    chmod 644 "$tmp"
    mv -f "$tmp" "$f"
  } 2>/dev/null || true
  return 0
}
```

**② 三个日备脚本接入**（`backup.sh` / `redis_backup.sh` / `media_backup.sh`，三处模式相同，以 `backup.sh` 为例）：

插入点 A —— `set -euo pipefail` 之后（约第 6 行）：

```bash
. /backup_status.sh
_backup_exit_handler() {
  local _rc=$?
  [ -n "${_BACKUP_SKIP:-}" ] && return 0
  backup_status_write "$_rc"
}
trap _backup_exit_handler EXIT
```

插入点 B —— 现有 flock 跳过分支（`backup.sh:24-27` 的 `exit 0` 处）加一行：

```bash
    echo "[$(date)] ⚠️ 上一次备份仍在执行, 本次跳过"
    _BACKUP_SKIP=1        # 新增: 跳过不算成功也不算失败, 不写状态
    exit 0
```

`redis_backup.sh:26`、`media_backup.sh:21` 的同构跳过分支同样加 `_BACKUP_SKIP=1`。

> **为什么用 EXIT trap 而不是脚本末尾写**：三个脚本均为 `set -euo pipefail`，任何 `exit 1` / 非零命令（pg_dump 失败、S3 重试耗尽、完整性校验失败、磁盘满）**立即终止、跳过末尾代码**——失败恰是最需要上报的路径，只有 trap 能覆盖全部退出路径。
>
> **为什么跳过分支要排除**：`exit 0` 是"上次还在跑"的防御性跳过，既非成功也非失败。若计入成功会推迟 Overdue 检测（掩盖停摆）；若计入失败则每次 30min 重叠都误报 critical。跳过 = 不写，指标保持前值，语义正确。
>
> **为什么 `verify.sh` / `restore_test.sh` 不接入**：现有 4 条告警均未引用验证/演练类指标，接入需新增指标与规则（范围蔓延）；其失败已走 docker logs 且周/季度频率低。列为后续可选项，不阻塞 N-2。

### 1.3 指标语义与告警配合（验收基准）

| 场景 | 指标表现 | 告警行为 |
|---|---|---|
| 每日 02:00 成功 | ts=运行结束时刻，counter 不变 | 无（`time()-ts` ≈ 24h < 25h 阈值 ✅） |
| 任一脚本失败 | ts 保持旧值，counter +1 | `BackupFailed`：`increase[1h]>0` 立即真 → `for: 5m` 后 firing；1h 窗口内不重复（自愈） |
| 连续 25h+ 无成功（含备份容器挂死） | ts 停更 | `BackupOverdue` firing（**免费获得备份容器存活检测**——容器死了 ts 必停更） |
| 首次部署（无文件） | 指标 absent | 两条规则均不触发（absent ≠ 0），首个 02:00 成功后自动进入监控态，**无部署期误报** |
| 卷丢失/文件损坏 | 按 0 重启计数 | 只少记历史失败，**无假阳性**（PromQL counter reset 语义） |
| 长任务跨 30min 与次日任务重叠 | flock 串行读-改-写 | 不丢失更新（最坏退化为一次重复计数，不产生漏报） |
| 状态写入失败（卷故障） | 指标停更但备份正常 | 可观测降级，业务无感；`BackupTextfileStale` 守卫（§3）报管道故障 |

三脚本共享同一对指标是有意设计：`BackupFailed` 捕获"任一备份失败"，`BackupOverdue` 捕获"全面停摆"，互补无缺口。

| 风险 | 等级 | 缓解 |
|---|---|---|

## 2. N-3 方案：blackbox TLS 证书探针

### 2.1 核心难点与解法（对抗审核重点）

**难点**：prometheus 的配置是 bind-mount 的静态文件（`./config/prometheus.yml`），**没有 env 渲染机制**；而探针目标 `https://<域名>/health/` 必须含真实生产域名（`DOMAIN` 只在 `.env` 中，且 `.env.example` 甚至没有 DOMAIN 条目）。直接把域名写死进 git 里的 `prometheus.yml` 违反项目"密钥/环境值走 .env"的既有约定。

**解法：域名渲染边车（sidecar）**——复用项目**已有且已验证的惯例**（nginx 的 `default.conf.tpl` + `entrypoint.sh` envsubst），新增一个极小的边车容器：读 `.env` 中的 `DOMAIN` → 渲染 `blackbox.yml.tpl` / `probes.yml.tpl` → 输出到与 prometheus 共享的卷。

> 为什么不选其他方案：
> - **写死域名进 prometheus.yml**：违反环境隔离约定（本项目 `.env` 注入模式），多环境（预发/生产）切换需改代码；
> - **`--enable-feature=remote-write-relabel`/env 展开**：Prometheus 2.53 不支持配置内 env 展开（无此特性）；
> - **blackbox 自身模板**：blackbox 只读 modules 配置，targets 来自 prometheus 侧，同样要解决"域名从哪来"；
> - **改用 `probe_http_url` 相对地址 + 直接探 `web:8000` 明文**：探针走的是 nginx 443 的 TLS 终结层，必须探真实公网链路才能测"证书"——探后端明文端口根本拿不到 TLS 信息，**不可行**；
> - **边车方案**：零新机制（与 nginx entrypoint 同构），容器常驻、启动时渲染一次（DOMAIN 变更本就需重启栈），故障面极小。

**第二个难点：探针必须能解析/到达生产域名**。blackbox 在 `asset-network`（bridge）内，`DOMAIN` 是公网域名 → 探针从容器内走公网回环到本机 nginx（hairpin），依赖宿主机 NAT 回环（Docker 默认 bridge 允许，但部分云厂商/防火墙可能拦截）。**缓解**：`/health/` 无限流无鉴权，且 15s 一次开销可忽略；若目标环境 hairpin 不通，备选方案 B（§2.3）用 `--sd-file` 指向 `https://127.0.0.1/health/` 并配置 SNI——但首选方案 A 测的是**真实客户端视角**，保真度最高。

### 2.2 文件改动清单（方案 A：边车渲染）

**① 新增 `docker/blackbox/Dockerfile`**（极小，基于 busybox 系）：

```dockerfile
# blackbox 配置渲染边车: 从 DOMAIN 环境变量渲染 blackbox/probes 配置
# 与 nginx entrypoint 的 envsubst 惯例同构
FROM busybox:1.36
COPY docker/blackbox/entrypoint.sh /entrypoint.sh
COPY docker/blackbox/blackbox.yml.tpl /templates/blackbox.yml.tpl
COPY docker/blackbox/probes.yml.tpl /templates/probes.yml.tpl
ENTRYPOINT ["/entrypoint.sh"]
```

**② 新增 `docker/blackbox/entrypoint.sh`**：

```sh
#!/bin/sh
# 渲染 blackbox 配置到共享卷 /rendered（与 prometheus 同卷）
# 幂等: 每次启动覆盖写入，DOMAIN 变更随栈重启生效
set -eu
[ -n "${DOMAIN:-}" ] || { echo "❌ DOMAIN 未设置，blackbox 配置无法渲染"; exit 1; }
umask 022
mkdir -p /rendered
# 单引号转义: 防止域名含特殊字符破坏 YAML（域名合法字符集下实际为恒等变换，纯防御）
esc=$(printf '%s' "$DOMAIN" | sed "s/'/'\\\\''/g")
sed "s|\${DOMAIN}|$esc|g" /templates/blackbox.yml.tpl > /rendered/blackbox.yml.tmp
sed "s|\${DOMAIN}|$esc|g" /templates/probes.yml.tpl    > /rendered/probes.yml.tmp
mv /rendered/blackbox.yml.tmp /rendered/blackbox.yml
mv /rendered/probes.yml.tmp /rendered/probes.yml
chmod 644 /rendered/*.yml
echo "blackbox config rendered for DOMAIN=$DOMAIN"
```

**③ 新增 `docker/blackbox/blackbox.yml.tpl`**（blackbox modules 配置，`http_2xx` 标准模块 + SNI 指向真实域名）：

```yaml
modules:
  https_health_2xx:
    prober: http
    timeout: 10s
    http:
      valid_http_versions: ["HTTP/1.1", "HTTP/2.0"]
      valid_status_codes: [200]
      method: GET
      no_follow_redirects: true
      fail_if_ssl: true          # 必须是 TLS，否则探针无意义
      fail_if_not_ssl: true
      tls_config:
        server_name: "${DOMAIN}"  # SNI 必须等于证书域名
        insecure: false
      headers:
        Host: ["${DOMAIN}"]
```

### 2.3 备选方案 B（hairpin 不通时启用）

若目标环境容器内无法公网回环（部分云/防火墙策略）：

1. `probes.yml.tpl` 改为 `targets: ["https://127.0.0.1/health/"]`（走宿主机回环直达 nginx，不经公网）；
2. `blackbox.yml.tpl` 的 `tls_config.server_name` 与 `headers.Host` **保持 `${DOMAIN}`**（SNI/Host 仍是真实域名，证书校验语义不变）；
3. 代价：失去"公网路径可达性"这一顺带收益（但 `ServiceDown`/`BlackboxTargetDown` 已覆盖服务可达性，证书校验不受影响）。

启用判据：部署后 V4 验收若 `probe_success == 0` 且宿主机直连 `curl -k https://<DOMAIN>/health/` 为 200 → 判定 hairpin 不通，切方案 B 重新渲染。

| 风险 | 等级 | 缓解 |
|---|---|---|
| 容器内 hairpin 回环被网络策略拦截 | 中 | 备选方案 B（§2.3），启用判据已给；首选 A 保留真实客户端视角 |

## 3. 两方案协同与执行顺序

### 3.0 N-3 部署前置检查（V-A 漏洞补充）

**背景**：N-3 的 blackbox-config-renderer 对空 `DOMAIN` 会 `exit 1`（可观测路径已设计），但理想情况是**部署前 fail-fast**，避免运维看到后续的 `TlsCertMetricMissing` 告警才后知后觉地查 DOMAIN。

**前置检查命令**（部署 N-3 前必须执行，部署脚本/CI 中应作为 gating 步骤）：

```bash
# N-3 V0 前置检查：保证 .env 中 DOMAIN 已配置且非空
# 执行位置：宿主机项目根目录
# 返回 0 = 通过，1 = 未配置
grep -q "^DOMAIN=" .env && [ -n "$(grep '^DOMAIN=' .env | cut -d= -f2-)" ] \
  && echo "✅ DOMAIN 已配置: $(grep '^DOMAIN=' .env | cut -d= -f2-)" \
  || { echo "❌ .env 中 DOMAIN 未配置或为空——请编辑 .env 添加 DOMAIN=<生产域名>（与 nginx/certbot 正在使用的值一致）"; exit 1; }
```

**集成点**：
- **手动部署**：`docker compose ... up -d` 前手工执行；
- **CI/CD pipeline**（`release-monitor.yml` 或同级 workflow）：在"部署 monitoring 栈" job 的第一步执行，失败则阻断后续步骤；
- **脚本封装**（可选）：可抽为 `scripts/check_n3_prereq.sh`，加入 release checklist。

**fail-fast 后的恢复路径**：
1. 编辑 `.env`：`DOMAIN=<生产域名>`；
2. 重启栈：`docker compose -f docker-compose.yml -f docker-compose.monitoring.yml up -d blackbox-config-renderer blackbox`；
3. 验收 §2.4 V1-V5；
4. `TlsCertMetricMissing` 若已 firing，会在数据恢复后 30min 内自动 resolved（无需手工 ack）。

### 3.1 部署顺序

```
commit-1 (N-2): backup_status.sh + 3 脚本接入 + Dockerfile + compose×2
   → 部署 → 验收 V1-V6 → 次日 02:00 自然验证一次真实写入
commit-2 (N-3): blackbox 边车 3 文件 + compose + prometheus.yml + alert_rules + .env.example
   → 部署前 V0 前置检查 → 验收 V1-V5 → 预发故障注入 V4b
```

- 两 commit **无依赖、可任意顺序、可单独回滚**；
- 若生产 `.env` 尚未定义 `DOMAIN`（取证确认 `.env.example` 无此条目，生产 `.env` 大概率也未显式写——nginx 用的 `${DOMAIN:-localhost}` 兜底掩盖了这一点），**N-3 部署前必须先在生产 `.env` 中显式补 `DOMAIN=<生产域名>`**（与 nginx/certbot 正在使用的值一致）。这是 N-3 的唯一前置人工动作，renderer 对空 DOMAIN 会 fail-fast（`exit 1` + 重启循环 + 告警），不会静默渲染出错误配置；
- 部署后**次日 09:00 前**做一次全链路人工确认：`time()-backup_last_success_timestamp < 36000`、`probe_ssl_earliest_cert_expiry > time()`、`up{job=~"node|blackbox"} == 1` 三项均真，即可将发布检查单中"确认 4 条无数据源规则已修复"一项勾选。

## 4. 对抗审核自查表

| 攻击点 | 方案回应 |
|---|---|
| "写状态失败会不会让备份失败？" | 不会。`{ ... } 2>/dev/null \|\| true` 整段吞错 + `return 0`，trap 中任何异常不影响脚本退出码传递（`_rc` 在 trap 入口先取） |
| "EXIT trap 会不会重复写？" | 不会。trap 只注册一次，每个脚本进程只触发一次；三脚本是三个独立 cron 进程，各自写各自的状态，语义正确 |
| "counter 会不会误报（容器重建/卷重置）？" | 值回落 → PromQL 按 counter reset 处理，`increase` 不产生假跳变；最坏是少记历史，不产生误告警 |
| "node-exporter 读不了 root 写的文件？" | 官方镜像 non-root 用户（UID 65534），方案显式 `umask 022` + 755/644 保证 world-readable；验收 V2 直接验证 |
| "blackbox 探 `/health/` 会不会被限流/记日志？" | 不会。`/health/` location 不在任何 `limit_req` 作用域，`access_log off` |
| "探针对后端有 DoS 风险吗？" | 15s/次 = 0.07 rps，`/health/` 是轻量检查（DB ping + Redis ping），可忽略 |
| "DOMAIN 渲染会不会注入恶意 YAML？" | 域名值来自部署者自有 `.env`（可信域）；renderer 仍做单引号转义防御；blackbox.yml.tpl 中 `${DOMAIN}` 只出现在 `server_name`/`Host` 两个字符串值位置，不改变 YAML 结构 |
| "prometheus 重启会不会让 `absent()` 守卫误报？" | `for: 30m` 吸收分钟级重启窗口；且该规则 severity=warning 非 critical，误报成本=一条飞书消息 |
| "为什么不直接写死域名/为什么不探 127.0.0.1？" | 写死违反环境隔离约定；探 127.0.0.1 明文后端拿不到 TLS 信息，方案 B 是 hairpin 不通时的降级而非默认 |
| "两栈分开部署怎么办？" | N-2 的命名卷共享依赖同项目目录启动（monitoring 栈文件头已有此前提声明）；N-3 的 `blackbox_rendered` 卷同栈内共享，无跨栈依赖 |
| "新增 busybox 镜像安全吗？" | 官方镜像、无网络、无特权、一次性渲染；与现有 6 个官方镜像（postgres/redis/nginx/prometheus 系）同信任级别 |
| "回滚会不会留半截状态？" | 两 commit 各自原子可逆；回滚后告警规则回到"无数据源休眠"（当前既有状态），不引入新风险面；卷可留可删 |
