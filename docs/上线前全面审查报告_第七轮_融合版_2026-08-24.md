 修复方案（仅改配置，不改业务代码）

 ** Step 1：确立“单一事实来源”——nginx 边缘层唯一下发**

 理由：nginx 直接服务 /static/、/media/（完全绕过 Django），这些路径只有 nginx 能覆盖；Django 无法成为全量来源。

 1a. Django 侧关闭全部安全头发射（config/settings/production.py）：

 ```python
   SECURE_HSTS_SECONDS = 0                      # HSTS 由边缘 nginx 唯一下发
   SECURE_HSTS_INCLUDE_SUBDOMAINS = False
   SECURE_HSTS_PRELOAD = False
   SECURE_CONTENT_TYPE_NOSNIFF = False          # 由 nginx 下发
   SECURE_REFERRER_POLICY = ""                  # 关闭默认 same-origin 双发
   # 移除 XFrameOptionsMiddleware（仅 production 的 MIDDLEWARE 覆写中移除，
   # base.py 保持不动，开发环境行为不变）
 ```

 1b. nginx 侧在代理 location 加去重护栏（防未来 Django 配置回退导致双发复活）：

 ```nginx
   # /api/ 等 proxy_pass 的 location 内追加：
   proxy_hide_header Strict-Transport-Security;
   proxy_hide_header X-Content-Type-Options;
   proxy_hide_header X-Frame-Options;
   proxy_hide_header Referrer-Policy;
   proxy_hide_header X-XSS-Protection;
 ```

 server 级 add_header ... always 保持现状，即整条链路每个头恰好一份。

 │ 注意 nginx 继承规则：location 块内出现任何 add_header 会取消继承 server 级定义。现有 /static/、/media/ 已正确显式重复，无需改动；新增任何带 add_header 的 location 必须同步重复安全头（tpl
 │ 中已有注释说明，保持）。

 ** Step 4：HSTS 安全性论证（对抗审核关键点）**

 - HSTS 由浏览器持久化、不可撤回。两处现值均已含 includeSubDomains; preload，收敛到较大值 63072000，任何已访问用户的 pin 只升不降，无回退风险
 - 若反向操作（Django 为唯一来源），静态资源将裸奔，故本方案方向唯一正确
 - SECURE_PROXY_SSL_HEADER 与 SECURE_SSL_REDIRECT=True 与本次改动正交，保持不动（否则会引入无限重定向回归）

 **Step 5：验证与回归屏障（CT-4）**

 1. 单副本断言（部署冒烟脚本）：
    ```bash
      for p in / /api/v1/ /static/ /media/; do
        n=$(curl -skI https://localhost$p | grep -ci "strict-transport-security"); [ "$n" = "1" ] || echo "FAIL $p"
      done
    ```
    同法遍历其余 5 个头。

 修复方案

 ### Step 1：迁移可逆性治理（优先级最高——这是数据安全项）

 1. 盘点断点：对全部 reverse_code=migrations.RunPython.noop 的迁移逐个评估：
     - 若反向操作确属无意义（如纯数据填充、回滚时新列即将被删除）→ 在文档中登记“不可逆点清单”，明确回滚下界（只能回滚到该迁移之后）
     - 若业务要求完整可逆 → 补写真实反向函数；无法安全还原的数据转换（如 JSON 迁移丢弃了旧格式信息），禁止硬造反向逻辑——错误的双向迁移比单向更危险
 2. 建立回滚 SOP 文档（不新增代码）：
     - 明确标准回滚流程 = docker compose down（web 层）→ python manage.py migrate <app> <target> → 回退镜像 tag → 重启
     - 强制前置条件：回滚前全量备份（复用 5.5 节 backup.sh 手动触发）
     - 引用根级 CT-6 三步验证作为回滚前检查（--plan 预览、禁用 zero 反向验证）
 3. CI 守护（migration-check.yml 已存在，追加一步）：检测新增迁移若含 noop 反向且未在 PR 描述注明理由，则告警——防止不可逆点继续滋生

 ### Step 2：镜像保留策略（低成本，先做）

 CI 新增 job step（build-push 之后）：

 ```yaml
   - name: Prune old images
     run: |
       # 列出仓库所有 sha 标签，保留最近 5 个，其余删除
       # Docker Hub API 或 hub-tool；亦可用 GHCR + crane delete
 ```

 配套要点：
 - latest 标签永不删除（部署入口依赖它）
 - 保留数量 5 个与建议一致，但需确认覆盖“当前生产运行版本 + 前一版本”至少两个，否则回滚无镜像可用——建议 CI 记录生产当前 sha 到 artifact，prune 时排除
 - 若迁到 GHCR，可用官方 retention API，比 Docker Hub API 更简单

 ### Step 3：发布回滚预案（单副本现实下的最小可行方案）

 不引入蓝绿/金丝雀基础设施（单副本 + compose 架构下过度设计），改为文档化快速回滚：

 ```sh
   # 回滚 = 指定历史镜像 tag 重新拉起
   IMAGE_TAG=<previous-sha> docker compose -f docker-compose.prod.yml up -d web
 ```

 配合 Step 1 的迁移下界规则：“镜像可任意回滚，数据库只能回滚到最近不可逆点之后”。

 ### Step 4：蓝绿/金丝雀的定位声明

 在文档中显式记录决策：当前单机 compose 部署、QPS 未达 OC-4 阈值，蓝绿/金丝雀暂缓立项；触发条件（多副本/高 QPS/K8s 迁移）满足时再评估。这既回应审计缺口，又避免为合规而过度建设。

 ### Step 5：演练与验证

 1. 回滚演练（staging）：部署 v_n → 制造迁移回滚场景 → 执行 SOP → 断言服务恢复且数据完好；每季度与 5.5 节恢复演练合并执行
 2. 镜像 prune 验证：手动触发 CI job，确认保留列表含生产当前版本
